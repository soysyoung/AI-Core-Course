## 날짜를 넘어 계속 나오는 핵심 원칙

| 원칙 | 어떻게 지키나 |
|---|---|
| test는 마지막까지 보관 | 모델 고르기·튜닝은 train/valid로만 하고, test는 최종 결과 확인에 딱 한 번 쓴다. test를 여러 번 보고 고르면 그 점수는 부풀려진다 |
| 에러 없음 ≠ 완료 | 출력된 숫자를 예상값과 비교하고 TODO 자리에 `None`·`pass`·`0` 같은 임시값이 남아 있지 않은지 확인한다 |
| 재현성 | `seed`를 고정하고 데이터 순서·버전을 기록해서 다시 실행해도 같은 숫자가 나오게 한다 |
| 원본 보존 | `data/`(원본)는 읽기만 하고 결과는 `outputs/`에 새 파일로 저장한다 |
| 근거 있는 답 | 답과 함께 출처(문서 ID, 위치)를 남겨서 다른 사람이 확인할 수 있게 한다 |

## Day6 (10/26) · 머신러닝 첫걸음 — 회귀와 분류

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| 머신러닝 | 입력 X와 정답 y의 짝을 많이 보여 주면 y ≈ f(X)가 되는 함수 f를 찾는다. 사람이 규칙을 직접 쓰지 않는 것이 핵심이다 |
| 특성(Feature) | 표의 열 중 예측에 쓰는 열. 단, 실행이 끝나야 알 수 있는 값(`elapsed_ms`)이나 정답(`failed`)은 넣으면 안 된다 |
| 정답(Label/Target) | 분류의 정답은 `failed`(0/1), 회귀의 정답은 `elapsed_ms`(숫자). 같은 표라도 문제에 따라 정답 열이 달라진다 |
| 학습(fit) | `model.fit(X_train, y_train)`. 오차가 가장 작아지도록 모델 내부 숫자(기울기 등)를 정한다 |
| 예측(predict) | `model.predict(X_new)`. 학습 때 정한 숫자를 그대로 써서 새 입력의 답을 계산한다 |
| 회귀 | 출력이 연속된 숫자. 예: 글자 수 800 → 걸린 시간 1,250ms |
| 분류 | 출력이 정해진 범주. 예: 글자 수 800, summary → 실패(1) |
| 선형회귀 | ŷ = a·x + b. 모든 점까지의 (오차)²의 합이 가장 작아지는 a(기울기)와 b(절편)를 찾는다 |
| 오차 | 오차 = 실제값 − 예측값. 예: 실제 1,200, 예측 1,000 → 오차 200 |
| MAE | 오차 절댓값의 평균. 오차가 +100, −300이면 (100+300)/2 = 200 |
| MSE | 오차 제곱의 평균. 같은 예시에서 (100²+300²)/2 = 50,000. 큰 오차(300)가 훨씬 크게 반영된다 |
| 로지스틱 회귀 | a·x + b를 시그모이드 함수에 넣어 0~1 사이 확률로 바꾼다. 확률이 높을수록 실패 쪽이다 |
| 임계값 | 확률 ≥ 0.5면 1, 아니면 0. 기준을 0.3으로 낮추면 실패를 더 많이 잡지만 잘못 잡는 것도 늘어난다 |
| KNN | 새 점과 모든 학습 점의 거리를 재서 가장 가까운 K개의 정답으로 다수결한다. 따로 "학습"하는 숫자가 없다 |
| K | K=1이면 가장 가까운 한 명만 따라가서 잡음에 흔들리고, K가 너무 크면 전체 다수결과 비슷해져 무뎌진다 |
| 스케일링 | 표준화: (x − 평균) ÷ 표준편차. 글자 수(수백~수천)와 0/1 열이 같은 무게로 거리 계산에 들어가게 한다. 평균과 표준편차는 train에서만 구한다 |
| train / valid / test | 예: 20건 → 12 / 4 / 4. train으로 학습, valid로 설정 비교, test로 최종 확인 |
| 데이터 누수 | 예: 전체 데이터로 평균을 구해 스케일링하면 test 정보가 train에 섞인다. 그러면 점수가 실제보다 좋게 나온다 |

## Day7 (10/27) · 나무 모델 — Decision Tree · Random Forest · XGBoost

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| 결정 트리 | "글자 수 ≤ 900?" 같은 질문으로 데이터를 둘로 나누고, 나뉜 쪽이 한 종류로 가장 깨끗해지는 질문을 골라 반복한다 |
| 깊이(depth) | 깊이 3이면 질문을 최대 3번 해서 최대 2³ = 8개의 칸으로 나뉜다 |
| 잎(leaf) | 마지막 칸에 있는 학습 데이터의 다수결(분류)이나 평균(회귀)이 예측값이 된다. 최소 잎 크기 2 = 한 칸에 최소 2건 |
| 과적합 | 깊이를 크게 하면 train 점수는 1.0에 가까워지는데 valid 점수는 떨어진다. 이 둘의 차이로 알아챈다 |
| 과소적합 | train과 valid 점수가 둘 다 낮다. 모델이 너무 단순하다는 신호다 |
| 랜덤 포레스트 | 데이터를 무작위로 다시 뽑고(부트스트랩) 질문 후보도 일부만 써서 나무 여러 그루(예: 20개)를 만든 뒤 다수결한다 |
| 앙상블 | 서로 다른 실수를 하는 모델들을 합치면 실수가 서로 상쇄되어 전체 성능이 안정된다 |
| XGBoost (부스팅) | 1번 나무의 예측과 정답의 차이(잔차)를 2번 나무가 맞히고, 이를 반복해 예측을 조금씩 더한다 |
| 특성 중요도 | 그 특성으로 나눌 때 데이터가 얼마나 깨끗해졌는지 모두 더한 값(MDI). 전체 합이 1이 되도록 맞춘다 |
| 순열 중요도 | valid에서 한 열만 무작위로 섞은 뒤 점수 하락폭을 잰다. 예: 0.80 → 0.60이면 중요도 0.20 |
| 교차검증(CV) | train을 3조각으로 나누면 [학습 2조각 + 평가 1조각]을 3번 돌려 점수 3개의 평균을 낸다 (기본필수: 학습 8·평가 4) |
| 원핫 인코딩 | task_type이 qa/summary면 `is_qa`, `is_summary` 두 열을 만들어 해당하는 칸만 1로 둔다 |
| 결측값 대체 | 빈칸을 train의 평균(숫자)이나 가장 많은 값(범주)으로 채운다. valid·test에도 train에서 구한 값을 그대로 쓴다 |
| Pipeline | `Pipeline([전처리, 모델])`을 CV에 통째로 넘기면 각 fold 안에서만 전처리를 학습하므로 누수가 생기지 않는다 |
| seed (재현성) | `random_state=42`처럼 고정하면 Forest의 무작위 뽑기가 매번 같아진다 |

## Day8 (10/28) · 평가지표와 군집

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| 혼동행렬 | TP(실패를 실패로), FP(성공을 실패로), FN(실패를 성공으로), TN(성공을 성공으로) 네 칸에 개수를 센다 |
| 정확도(Accuracy) | (TP+TN) ÷ 전체. 성공 18·실패 2인 데이터에서 전부 "성공"이라고 해도 0.9가 나온다는 함정이 있다 |
| 정밀도(Precision) | TP ÷ (TP+FP). "실패"라고 4번 말했는데 3번 맞았으면 0.75 |
| 재현율(Recall) | TP ÷ (TP+FN). 진짜 실패 4건 중 3건을 잡았으면 0.75. 놓치면 큰일 나는 문제에서 중요하다 |
| F1 | 2 × P × R ÷ (P + R). 둘 중 하나가 0이면 F1도 0이 된다. 실패를 하나도 못 잡으면 F1 = 0 |
| ROC 곡선 | 임계값을 1→0으로 내리면서 (거짓 경보율, 재현율) 점을 찍어 이은 선 |
| AUC | ROC 곡선 아래 넓이. 0.5면 동전 던지기, 1.0이면 완벽하다. 판정값이 아니라 확률(`predict_proba`)로 계산한다 |
| RMSE | √MSE. 오차가 +100, −300이면 √50,000 ≈ 224ms로, 원래 단위(ms)로 돌아온다 |
| 비지도 학습 | 입력 X만 있고 정답 y가 없다. 군집 결과는 "맞다/틀리다"로 채점할 수 없다 |
| K-Means 군집 | ① 중심 K개를 정하고 ② 각 점을 가장 가까운 중심에 배정한 뒤 ③ 중심을 무리의 평균으로 옮기고, ②③을 반복한다 |
| 군집 번호 | 0, 1, 2는 실행 순서상 붙인 이름일 뿐이다. 다시 돌리면 번호가 바뀔 수 있고, 크기 비교도 의미가 없다 |
| 평가 계획 | "주 지표는 F1, 동점이면 AUC, test는 마지막에 1번"처럼 결과를 보기 전에 기록해 둔다 |

## Day9 (10/29) · 딥러닝 기초 — GPU · Tensor · Autograd · ANN

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| GPU | 수천 개의 작은 코어가 행렬 곱셈 같은 같은 종류의 계산을 동시에 처리한다 |
| CUDA | `torch.cuda.is_available()`이 True면 GPU를 쓸 수 있다. False면 CPU로 돌려도 결과는 같고 속도만 다르다 |
| PyTorch | 텐서 계산, 자동 미분, 신경망 층(`nn.Linear` 등), 학습 도구(옵티마이저)를 제공한다 |
| Tensor | 0차원 = 숫자 하나, 1차원 = 목록, 2차원 = 표, 3차원 이상 = 표를 여러 장 쌓은 것 |
| shape | 표 20행 × 2열이면 `(20, 2)`. 층끼리 연결할 때 shape이 맞지 않으면 에러가 난다 |
| device | `x.to("cuda")`. 모델과 데이터가 같은 device에 있어야 계산할 수 있다 |
| 기울기(Gradient) | y = x²에서 x = 3일 때 기울기는 2x = 6. x를 조금 늘리면 y가 약 6배로 늘어난다는 뜻이다 |
| Autograd | `requires_grad=True`인 값으로 계산한 뒤 `loss.backward()`를 호출하면 각 값의 기울기가 `.grad`에 저장된다 |
| 경사하강법 | 새 값 = 현재 값 − 학습률 × 기울기. 기울기의 반대 방향으로 움직여 손실을 줄인다 |
| 학습률 | 0.1 × 기울기 6 = 0.6만큼 이동한다. 너무 크면 최솟값을 지나쳐 발산하고, 너무 작으면 아주 느리다 |
| 인공신경망(ANN) | 입력 → [선형 변환 → 활성화] × 여러 층 → 출력. 예: 2 → 8 → 1 |
| 가중치 / 편향 | 한 층은 y = W·x + b. `nn.Linear(2, 8)`이면 W는 8×2 = 16개, b는 8개, 모두 학습 대상이다 |
| 활성화 함수(ReLU) | ReLU(x) = max(0, x). 이게 없으면 층을 아무리 쌓아도 결국 직선 하나와 같다 |
| 손실 함수 | 회귀는 MSE, 분류는 교차 엔트로피(정답 확률이 낮을수록 벌점이 커짐)를 주로 쓴다 |
| 배치 | 100건을 배치 크기 20으로 나누면 1에폭에 5번 가중치를 고친다 |
| 에폭(Epoch) | 10에폭 = 전체 데이터를 10바퀴 학습. 배치 5개 × 10 = 가중치 수정 50번 |
| 학습 루프 | `zero_grad()` → 예측 → `loss` 계산 → `backward()` → `step()`. 기울기를 먼저 0으로 지우지 않으면 이전 값이 쌓인다 |
| 체크포인트 | `torch.save(model.state_dict(), "model.pt")`로 가중치를 저장하고 `load_state_dict`로 불러온다 |

## Day10 (10/30) · 학습 안정화

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| 옵티마이저 | SGD는 "값 − 학습률 × 기울기"를 그대로 쓴다. Adam은 값마다 이동 크기를 자동으로 조절한다 |
| 모멘텀 | 속도 = 0.9 × 이전 속도 + 기울기. 방향이 계속 같으면 가속되고, 지그재그는 서로 상쇄된다 |
| 학습 곡선 | train 손실과 valid 손실을 같이 그린다. train만 계속 내려가고 valid가 다시 올라가기 시작하면 과적합이다 |
| 배치 크기 | 작을수록 한 번에 보는 정보가 적어 곡선이 들쭉날쭉하고, 클수록 매끄럽지만 수정 횟수가 줄어든다 |
| 모델 너비 | 은닉층 뉴런이 4개 → 64개면 표현력은 커지지만 가중치 수가 늘어나 과적합하기 쉽다 |
| 드롭아웃 | `Dropout(0.5)`: 학습 때 뉴런의 50%를 무작위로 0으로 만든다. 평가 때는 끄고 모든 뉴런을 쓴다 |
| 배치 정규화 | 배치 안에서 값을 평균 0, 표준편차 1로 맞춘 뒤 학습 가능한 배율과 이동값을 적용한다 |
| train 모드 / eval 모드 | `model.train()` / `model.eval()`. eval에서는 드롭아웃이 꺼지고, 배치 정규화는 학습 중 저장한 평균을 쓴다 |
| 최적 상태 복원 | 에폭마다 valid 손실을 확인해서 가장 낮았던 시점의 가중치를 복사해 두고, 학습이 끝나면 그 가중치로 되돌린다 |

## Day11 (11/2) · CNN · 이미지 분류 · 전이학습

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| 이미지 텐서 | 64×64 컬러 사진은 shape `(3, 64, 64)`, 배치 8장이면 `(8, 3, 64, 64)`. 0~255 값을 0~1로 나눠 쓴다 |
| 합성곱(Convolution) | 3×3 필터를 한 칸씩 옮기며 겹친 9개 칸을 곱해 더한다. 결과가 크면 그 위치에 필터의 무늬가 있다는 뜻이다 |
| 필터(커널) | 예: [[−1,0,1]]은 왼쪽과 오른쪽의 밝기 차이(세로 경계)에 반응한다. CNN은 이 숫자들을 스스로 학습한다 |
| 채널 | `Conv2d(3, 16, 3)`: 입력 3채널(RGB)을 받아 필터 16개를 써서 16채널 출력을 만든다 |
| 풀링 | 2×2 최대 풀링: 4칸 중 가장 큰 값 하나만 남겨 64×64 → 32×32로 줄인다. 학습할 숫자는 없다 |
| CNN | [합성곱 → ReLU → 풀링] 반복으로 특징을 뽑고, 펼친(flatten) 뒤 선형 층으로 클래스 점수를 낸다 |
| ImageFolder | `train/horizontal/*.png` → 정답 0, `train/vertical/*.png` → 정답 1. 폴더 이름의 알파벳 순서로 번호가 정해진다 |
| 데이터 증강 | 좌우 뒤집기, 작은 회전 등은 학습 데이터에만 적용한다. valid/test는 원본 그대로 평가한다 |
| 전이학습 | 앞부분(특징 추출기)은 가져온 것을 쓰고 마지막 층만 내 클래스 수(예: 2)에 맞게 새로 만든다 |
| 사전학습 가중치 | ResNet18을 ImageNet(약 120만 장, 1,000종류)으로 학습한 가중치. 처음 쓸 때 파일(약 45MB)을 내려받는다 |
| 동결(Freeze) | `param.requires_grad = False`로 설정하면 그 가중치는 기울기를 계산하지 않아 바뀌지 않는다. 학습할 파라미터 수가 크게 줄어든다 |
| 벤치마크 | 같은 입력으로 여러 번 실행해 평균 시간을 잰다. 처음 몇 번(warm-up)은 느리니 제외하고, CPU면 GPU 메모리는 N/A로 적는다 |

## Day12 (11/3) · 순서가 있는 데이터 — RNN · LSTM · Attention

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| 시퀀스 | 입력 shape이 `(배치, 길이, 특성 수)`. 같은 숫자라도 순서가 바뀌면 다른 데이터다 |
| 시계열 | 시간 간격이 일정한 관측값. 예: 1분마다 기록한 요청 수 |
| Window | [1,2,3,4,5,6]을 길이 3으로 자르면 [1,2,3]→4, [2,3,4]→5, [3,4,5]→6처럼 입력-정답 쌍이 생긴다 |
| 시간순 분할 | 100개 → 앞 60(train) / 다음 20(valid) / 마지막 20(test). 먼저 나눈 다음 각 구간 안에서 Window를 만든다 |
| Padding | 길이 3, 5인 문장을 [a,b,c,0,0], [a,b,c,d,e]로 맞춘다. 원래 길이는 따로 기억해 둔다 |
| 마스크 | [1,1,1,0,0]처럼 진짜 칸은 1, 패딩 칸은 0. 평균이나 Attention 계산에서 0인 칸을 뺀다 |
| RNN | h_t = tanh(W·x_t + U·h_(t−1) + b). 이전 기억 h와 현재 입력 x를 섞어 새 기억을 만들고, 같은 가중치를 매 칸 재사용한다 |
| LSTM | 망각문(얼마나 지울지), 입력문(얼마나 새로 쓸지), 출력문(얼마나 내보낼지)이 0~1 값으로 기억 흐름을 조절한다. 긴 순서에서도 앞 내용이 잘 남는다 |
| Autoencoder | 입력(예: 20개 값) → 인코더 → 압축(예: 4개) → 디코더 → 복원(20개). 손실은 입력과 복원의 차이다 |
| 재구성 오차 / 이상탐지 | 정상 데이터로만 학습한 뒤 valid에서 오차 기준(예: 상위 5%)을 정한다. 기준보다 오차가 크면 이상으로 판정한다 |
| Attention | 각 위치와 기준 사이의 점수를 구해 softmax로 합이 1인 가중치로 만들고, 그 가중치로 값들을 가중 평균한다 |

## Day13 (11/4) · OpenCV 이미지·영상 전처리

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| OpenCV | `cv2.imread`로 읽으면 NumPy 배열 `(높이, 너비, 3)`이 된다. 파일이 없으면 에러 대신 `None`을 돌려주니 꼭 확인한다 |

| 엣지 검출(Canny) | 밝기 변화량을 구한 뒤 두 임계값을 쓴다. 높은 값을 넘으면 확실한 경계, 둘 사이면 확실한 경계와 이어질 때만 경계로 인정한다 |
| 이진화(Threshold) | 기준 127: 픽셀 > 127 → 255, 아니면 0. 결과에는 0과 255 두 값만 남는다 |
| 모폴로지 | 침식은 주변이 모두 흰색일 때만 흰색으로 남기고, 팽창은 주변에 흰색이 하나라도 있으면 흰색으로 만든다. 열기(침식→팽창)는 작은 점을 지운다 |
| 프레임 / FPS | 30 FPS 영상 10초 = 프레임 300장. `cv2.VideoCapture`로 한 장씩 읽고, 끝나면 `release()`로 닫는다 |

## Day14 (11/5) · 전이학습 심화와 오류 분석

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| Dataset / DataLoader | Dataset은 `len()`과 `[i]`로 (이미지, 정답)을 하나씩 준다. DataLoader는 이를 배치로 묶고 train에서만 섞는다(`shuffle=True`) |
| 헤드(Head) | ResNet18 마지막 층 `fc`(512 → 1000)를 `nn.Linear(512, 클래스 수)`로 바꿔 끼운다 |
| 파인튜닝 | 1단계: 헤드만 학습 → 2단계: 마지막 블록까지 풀어 더 작은 학습률로 함께 학습한다 |
| 클래스 불균형 | 정상 90 : 불량 10이면 전부 "정상"이라고 해도 정확도가 90%다. 그래서 클래스별 재현율을 따로 본다 |
| 가중 손실 | 클래스 무게를 개수에 반비례하게 준다. 예: 정상 1, 불량 9. 불량을 틀리면 벌점이 9배다 |
| 오류 분석 | 틀린 예시를 (정답, 예측, 확률)과 함께 표로 모으고 공통점(어두움, 흐림 등)을 찾아 원인을 추정한다 |
| Grad-CAM | 마지막 합성곱 층의 특징 지도에 "그 클래스 점수에 대한 기울기"로 무게를 줘서 더한 뒤, 원본 크기로 키워 색으로 겹쳐 보여 준다 |

## Day15 (11/6) · 객체 탐지 — IoU · YOLO

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| 객체 탐지 | 출력 하나 = (클래스, 신뢰도, 상자 좌표). 사진 한 장에서 출력이 여러 개일 수 있다 |
| 바운딩 박스 | xyxy = (왼쪽 x, 위쪽 y, 오른쪽 x, 아래쪽 y), xywh = (중심 x, 중심 y, 너비, 높이). 형식을 섞으면 위치가 틀어진다 |
| IoU | 상자 A·B 넓이가 각 100이고 겹친 넓이가 50이면 50 ÷ (100+100−50) = 0.33 |
| 라벨 파일 | YOLO 형식: 한 줄에 `클래스 중심x 중심y 너비 높이`, 좌표는 사진 크기로 나눈 0~1 값. 예: `0 0.5 0.5 0.2 0.3` |
| YOLO | 사진을 격자로 나누고 각 칸에서 상자와 클래스를 한 번의 신경망 계산으로 동시에 예측한다 |
| 신뢰도(Confidence) | 기준(예: 0.25)보다 낮은 상자는 버린다. 같은 물체에 겹친 상자는 IoU가 높으면 신뢰도 높은 것만 남긴다(NMS) |
| mAP50 | IoU ≥ 0.5를 맞힌 것으로 보고 클래스마다 정밀도-재현율 곡선 아래 넓이(AP)를 구한 뒤 클래스끼리 평균한다 |
| 추적(Tracking) | 이전 프레임 상자와 현재 프레임 상자의 IoU·위치를 비교해 같은 물체로 판단하면 같은 ID를 이어 준다 |

## Day16 (11/9) · OCR · VLM · 엣지 추론

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| OCR | 글자 영역 찾기 → 글자 인식 순서로 진행하며, 결과는 (글자, 위치 상자, 신뢰도)로 나온다 |
| 기울기 보정 | 문서의 네 꼭짓점을 찾아 투시 변환으로 직사각형으로 편다. 그레이스케일·이진화도 함께 하면 인식률이 오른다 |

| 엣지 추론 | 기기 안에서 실행하면 네트워크 지연이 없고 데이터가 밖으로 나가지 않는다. 대신 메모리와 속도 한계 때문에 작은 모델을 쓴다 |
| Hybrid | 예: 글자는 OCR로 빠르게 읽고, 해석이 애매한 부분만 VLM에 물어 비용과 정확도를 같이 잡는다 |

## Day18 (11/11) · PostgreSQL · SQL · ERD

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| 데이터베이스 | 여러 프로그램이 동시에 읽고 써도 데이터가 깨지지 않게 관리해 주는 서버 프로그램 |
| 관계형 DB / 테이블 | 예: `users → orders → order_items ← items ← categories`처럼 표들이 키로 연결된다 |
| 행 / 열 | 열마다 타입이 정해져 있다 (`price INTEGER`, `email TEXT`). 행은 데이터 한 건이다 |
| PostgreSQL | 서버는 기본 포트 5432를 쓰고, pgAdmin(화면)이나 psql(명령줄)로 접속한다 |
| SQL | 무엇을 원하는지만 쓰면 DB가 가져오는 방법을 알아서 정한다 |
| SELECT · WHERE · ORDER BY · LIMIT | `SELECT name, price FROM items WHERE price >= 10000 ORDER BY price DESC LIMIT 2;` → 1만 원 이상 중 비싼 2개 |
| 기본키(PK) | `id`처럼 중복과 빈칸이 허용되지 않는 열. 이 값으로 행 하나를 정확히 찾는다 |
| 외래키(FK) | `orders.user_id`가 `users.id`를 가리킨다. 없는 사용자의 주문은 넣을 수 없다 |
| JOIN | `FROM orders o JOIN users u ON o.user_id = u.id` → 주문 행 옆에 사용자 정보를 붙인다 |
| 집계(GROUP BY) | `SELECT user_id, COUNT(*), SUM(total) FROM orders GROUP BY user_id;` → 사용자별 주문 수와 합계 |
| 제약조건 | `NOT NULL`(빈칸 금지), `UNIQUE`(중복 금지), `CHECK (price >= 0)`(조건 검사) |
| ERD | 표는 상자, 관계는 선으로 그린다. 1:N 관계면 N쪽 표에 외래키가 있다 (사용자 1명 : 주문 여러 개) |
| 트랜잭션 | `BEGIN; 재고 감소; 주문 추가; COMMIT;` 중간에 실패하면 둘 다 반영되지 않는다 |
| ROLLBACK | `BEGIN; UPDATE ...; ROLLBACK;`으로 연습한 변경을 되돌려 원래 데이터를 지킨다 |
| 인덱스 | 정렬된 목차가 있으면 전체 행을 다 훑지 않고 바로 찾는다. `EXPLAIN`으로 실제 인덱스를 썼는지 확인한다 |

## Day23 (11/18) · Embedding · pgvector

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| 임베딩 | 문장 → 모델 → [0.12, −0.03, ..., 0.08] (384개). 뜻이 비슷한 문장은 가까운 위치의 벡터가 된다 |
| 벡터 / 차원 | 2차원 벡터 (3, 4)의 길이는 √(3²+4²) = 5. 384차원도 계산 방식은 같다 |
| 유사도 | 내적: (1,2)·(3,4) = 1×3 + 2×4 = 11. 값이 클수록 비슷하다 |
| 코사인 유사도 | cos = 내적 ÷ (길이 × 길이). 같은 방향이면 1, 직각이면 0. 길이를 1로 맞춰 두면(정규화) 내적과 같아진다 |
| E5 모델 | `query: 반품 기간은?`, `passage: 반품은 7일 이내...`처럼 접두어를 붙여 넣고, 384차원 벡터를 얻는다 |
| pgvector | `CREATE EXTENSION vector;` 후 `embedding vector(384)` 열을 만든다. `<=>`는 코사인 거리(= 1 − 코사인 유사도)다 |
| Top-k 검색 | `ORDER BY embedding <=> 질문벡터 LIMIT 5` → 거리가 가장 가까운 5개를 가져온다 |
| HNSW 인덱스 | 여러 층의 연결 지도에서 위층은 크게, 아래층은 촘촘하게 이동하며 가까운 점을 찾는다. 전부 비교하지 않으니 빠르지만 근사값이다 |
| 관련성 평가 | 질문마다 정답 문서를 정해 두고, Top-k 안에 들어왔는지 세어 검색 품질을 숫자로 확인한다 |
| Retriever | 입력은 질문 문자열, 출력은 (문서, 점수) 목록. 내부에서는 임베딩 → 벡터 검색 → 정렬 순서로 동작한다 |

## Day24 (11/19) · 문서 파싱 · 청킹 · 인덱싱

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| 수집(Collection) | 파일마다 (경로, 크기, 해시, 버전)을 Manifest에 기록해서 무엇을 언제 넣었는지 추적한다 |
| 해시(SHA-256) | 파일의 바이트를 넣으면 64자리 16진수가 나온다. 해시가 같으면 같은 파일이니 다시 처리하지 않는다 |
| 파싱 | TXT는 UTF-8로 읽고, HTML은 태그를 걷어 내고 본문만 남기고, PDF는 페이지별로 글자를 뽑고, 스캔 이미지면 OCR을 쓴다 |
| 정제(Cleaning) | 줄바꿈 `\r\n`(CRLF) → `\n`, 연속 공백 정리 등. 바꾼 내용과 정제 후 해시를 기록한다 |
| 유니코드 정규화(NFC/NFKC) | NFC: 'ㅎ+ㅏ+ㄴ'으로 쪼개진 글자를 '한' 한 글자로 합친다. NFKC는 '①' → '1'처럼 모양이 다른 글자까지 통일한다 |
| 청킹(Chunking) | 1,000자 문서를 크기 400, 겹침 100으로 자르면 [0~400], [300~700], [600~1000] 세 조각이 나온다 |
| Chunk Size / Overlap | 조각이 너무 크면 검색이 흐릿해지고, 너무 작으면 문맥이 잘린다. 겹침은 경계에서 문장이 끊기는 것을 보완한다 |
| Offset | 조각마다 (start, end)를 저장해 두면 `원문[start:end] == 조각 내용`인지 언제든 확인할 수 있다 |
| 토큰 / 토크나이저 | "임베딩 모델" → ["임", "##베딩", "모델"]처럼 쪼갠다. 모델마다 최대 토큰 수(예: 512)가 정해져 있다 |
| 검증(Coverage·Gap) | 조각들의 offset을 정렬해 이어 붙였을 때 빠진 구간(Gap)이 없는지, 원문을 얼마나 덮는지(Coverage)를 계산한다 |
| 격리(Quarantine) | 검증에 실패한 문서는 별도 목록으로 빼고 이유를 기록한다. 고칠 때까지 검색 대상에 넣지 않는다 |
| 메타데이터 | `{"source": "manual.pdf", "page": 3, "pipeline_version": "v2"}`. 검색할 때 필터 조건으로도 쓴다 |
| 인용(Citation) | 답에 쓴 조각의 메타데이터(파일, 페이지, 위치)를 [1], [2] 형태로 연결해 보여 준다 |
| 인덱싱 | 새 버전을 Stage(임시 공간)에 먼저 넣고 검증한 뒤 Publish(공개)로 한 번에 바꾼다. 실패하면 이전 버전을 유지한다 |
| Ingestion 파이프라인 | 단계마다 입력과 출력, 개수를 기록하는 보고서(Report)를 남긴다. 다시 실행해도 같은 결과가 나와야 한다 |

## Day25 (11/20) · 개인 프로젝트 — 보고서 처리 Agent

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| 요구사항 명세서(SRS) | 요구사항마다 ID를 붙인다 (예: FR-01 보고서 업로드). 입력·출력·완료 조건을 한 줄씩 적는다 |
| ERD → API → JSON | 어떤 표에 저장할지 → 어떤 주소와 메서드로 요청할지 → 요청·응답 본문의 키와 타입 순서로 설계를 좁혀 간다 |
| API 계약 | 예: `POST /reports` → 201 + `{"id": 1, "status": "pending"}`, 필수 칸이 빠지면 422. 이 표만 보고 테스트를 쓸 수 있어야 한다 |
| 완료 체크리스트 | "요청 → 예상 응답 → 실제 응답 → 통과 여부"를 표로 확인한다 |
| 추적성 | 요구사항 ID ↔ 코드 파일 ↔ 테스트 이름을 표로 이어서 빠진 요구사항이 없는지 확인한다 |
| Agent | 목표 → 계획 → 도구 호출(검색, DB 조회 등) → 결과 확인 → 다음 행동을 반복한다. 단계마다 상태를 기록한다 |

## Day26 (11/23) · Basic RAG & LangChain

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| LLM | 앞의 토큰들을 보고 다음 토큰의 확률을 계산해 하나씩 이어 쓴다. 학습 시점 이후의 정보나 회사 내부 문서는 모른다 |
| 할루시네이션 | 확률적으로 그럴듯한 문장을 만들 뿐이라서 사실 확인 없이 틀린 숫자나 출처를 지어낼 수 있다 |
| RAG | ① 질문 임베딩 → ② Top-k 문서 검색 → ③ 프롬프트에 "아래 문서만 근거로 답하라" + 문서 → ④ LLM이 답 생성 |
| Hit | (문서 ID, 내용, 점수, 메타데이터) 한 묶음. Top-5 검색이면 Hit이 5개다 |
| Context | Hit들의 내용을 번호와 함께 이어 붙인 텍스트. 너무 길면 모델의 입력 한도를 넘으니 개수나 길이를 제한한다 |
| LangChain | 검색기, 프롬프트, 모델, 출력 파서를 같은 방식(Runnable)으로 다루게 해 준다 |
| Document | `Document(page_content="본문", metadata={"source": "a.pdf", "page": 2})` |
| Prompt 템플릿 | `"문서: {context}\n질문: {question}"`의 `{}` 자리에 실제 값을 채워 메시지를 만든다 |
| Chat Model | system(규칙), user(질문) 메시지 목록을 입력받아 assistant 메시지를 돌려준다. temperature가 낮을수록 답이 일정하다 |
| Runnable / invoke | 모든 부품이 `.invoke(입력)` → 출력이라는 같은 사용법을 가진다 |
| Chain | `prompt \| model \| parser`처럼 `\|`로 이으면 앞 부품의 출력이 다음 부품의 입력이 된다 |
| Structured Output | `{"answer": str, "sources": list}`처럼 형식을 지정해 받으면 코드에서 바로 꺼내 쓸 수 있다 |
| Validation | 형식(필수 키가 있나), 근거(인용한 출처가 실제 검색 결과에 있나)를 확인하고 실패하면 "모름"이나 에러를 돌려준다 |
| RAG API | `POST /ask` + `{"question": "..."}` → `{"answer": "...", "sources": [...]}`처럼 체인을 엔드포인트로 감싼다 |

## Day27 (11/24) · RAG 검색 개선 — Query 최적화 · Reranking

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| 실패 진단 | 정답 문서가 Top-k 안에 없으면 검색 실패, 있는데 답이 틀렸으면 생성 실패다. 고칠 곳이 달라진다 |
| 쿼리 재작성 | "그거 언제까지 돼?" → "상품 반품 신청 기한은 며칠인가?" 대명사와 생략을 채워 검색어를 분명하게 만든다 |
| Multi-query | 질문 하나로 표현이 다른 질문 3개를 만들어 각각 Top-5를 검색하면 후보가 최대 15개 모인다 |
| 중복 제거 | 같은 청크 ID가 여러 검색에서 나오면 하나만 남긴다. 예: 15개 → 9개 |
| 후보 검색 | 1단계에서 Top-20처럼 넉넉히 가져와 정답을 놓칠 확률을 줄이고, 2단계에서 줄인다 |
| 리랭킹(Reranking) | 후보 20개를 더 정확한 모델로 다시 점수 매겨 정렬하고 상위 5개만 LLM에 넘긴다 |
| Bi-encoder | 문서 벡터를 미리 계산해서 저장할 수 있어 수백만 개도 빠르게 검색한다. 질문과 문서가 서로를 보지 못한 채 비교된다 |
| Cross-encoder | [질문 + 문서]를 한 입력으로 넣어 관련 점수 하나를 낸다. 후보마다 다시 계산해야 해서 후보 수십 개에만 쓴다 |
| Before / After 비교 | 같은 질문 세트로 리랭킹 전후의 정답 문서 순위와 Recall@k를 표로 나란히 비교한다 |

## Day28 (11/25) · RAG 평가

| 용어 | 어떻게 동작하나 · 예시 |
|---|---|
| Gold 데이터셋 | `{"question": "...", "gold_chunk_ids": ["c3", "c7"]}`처럼 질문마다 정답 근거 조각을 정해 둔다 |
| 무정답 질문(No-answer) | Gold가 비어 있는 질문. 재현율 계산에서는 빼고(값 None), "근거 없음"이라고 답했는지를 따로 확인한다 |
| Recall@k | Gold 2개 중 Top-5 안에 1개가 있으면 1/2 = 0.5 |
| Precision@k | Top-5 중 Gold가 1개면 1/5 = 0.2 |
| 순위 지표(MRR·nDCG) | MRR: 첫 정답이 3등이면 1/3. 질문마다 구해 평균한다. nDCG는 더 관련 있는 문서가 앞에 올수록 높은 점수를 준다 |
| Claim | "반품은 7일 이내 가능하며 배송비는 고객 부담이다" → Claim 2개 |
| 근거 일치 | Claim 2개 중 1개만 Context에 적혀 있으면 1/2 = 0.5 |
| 질문 적합성 / 정답성 | 질문에 맞는 내용을 답했는지와 그 내용이 Gold 정답과 맞는지를 따로 채점한다. 근거는 있지만 엉뚱한 답일 수도 있다 |
| Target / Evaluator | Target에는 질문만 넣고 정답은 넣지 않는다. Evaluator가 Target의 출력과 Gold를 비교해 점수를 낸다 |
| 한 번에 하나만 바꾸기 | 기준 설정에서 리랭커만 켜고 측정 → 끄고 쿼리 재작성만 켜고 측정. 바꾼 것 하나와 점수 변화를 짝지어 기록한다 |
| 오프라인 / 라이브 | `--offline`은 저장된 고정 결과로 수식을 연습하고, `--live`는 실제 모델·DB를 호출한다. 오프라인 점수를 실제 성능이라고 하지 않는다 |
| 실패 단계 진단 | System 오류? → 후보에 Gold 없음? → Context에 Gold 없음? → 답변이 근거와 다름? 순서로 확인한다. 후보에 없는 문서는 리랭커가 되살릴 수 없으니 그때는 검색부터 고친다 |
| invoke | `chain = RunnableLambda(f)`로 정의만 하고, `chain.invoke({"question": ...})`를 불러야 실행된다. 입력에는 Gold를 빼고 넣는다 |
| 4가지 비교군 | Baseline Recall 0.50, Rewrite만 0.60, Rerank만 0.55, 둘 다 0.70 → 각 기능의 효과를 따로 볼 수 있다. 같은 Gold·같은 k로만 비교한다 |
| 배포 보류(회귀 판정) | 질문별 변화량 = After − Before (No-answer는 제외). Recall이 Baseline보다 낮거나 실행 오류가 하나라도 있으면 "보류"와 이유를 기록한다 |
| Agent 1차 관문 | Recall·MRR이 기준 이상 + 출처 확인 성공 + 실행 오류 0 + 사람 검토·접근 제어 확인을 모두 만족해야 통과. 통과해도 운영 배포 승인은 아니다 |
