```
[머신러닝]   표 데이터 → 예측        해석 가능성 ↔ 표현력 (선형 → 트리 → 부스팅)      Day6~8
   ↓
[딥러닝]     텐서 → 미분 가능한 층   데이터·연산량 ↔ 특징 설계를 사람이 안 해도 됨    Day9~10
   ↓
[비전/순서]  공간·시간 구조 활용     귀납 편향(합성곱·순환) ↔ 일반성(Attention)     Day11~16
   ↓
[서비스]     HTTP ↔ DB               유연성 ↔ 일관성(스키마·제약·트랜잭션)          Day17~18

[RAG]        검색 + 생성             재현율(후보 넓게) ↔ 정밀도·비용(리랭킹·Context) Day23~28
```

## 날짜를 넘어 계속 나오는 핵심 원칙 — 왜 지키나

| 원칙 | 왜 필요한가 · 어기면 생기는 일 |
|---|---|
| test는 마지막까지 보관 | 모델 선택도 일종의 학습이다. test로 여러 후보를 고르면 test에 과적합한 것이 되어 보고한 점수가 낙관적으로 편향된다(선택 편향). valid가 "선택용", test가 "보고용"으로 역할이 다르다 |
| 에러 없음 ≠ 완료 | 예외는 "형식" 오류만 잡는다. 수식 실수, 누수, 임시값은 조용히 그럴듯한 숫자를 낸다. 그래서 손으로 계산한 작은 예시와 대조하는 검증(Oracle test)이 필요하다 |
| 재현성 | 결과 차이가 "설정을 바꿔서"인지 "난수가 달라서"인지 구분하려면 seed·데이터 버전·코드 버전이 고정돼야 한다. 단, GPU 연산은 seed를 고정해도 비결정적일 수 있어 여러 seed의 평균·분산을 같이 보는 게 더 정직하다 |
| 원본 보존 | 원본을 덮어쓰면 파이프라인을 다시 돌려 검증할 기준점이 사라진다. 불변(immutable) 입력 + 파생 출력 구조는 디버깅과 감사(audit)의 전제다 |
| 근거 있는 답 | 정확도만으로는 "왜 그 답인지" 확인할 수 없다. 출처를 남기면 틀렸을 때 검색·데이터·생성 중 어디가 원인인지 추적할 수 있고, 사용자가 직접 검증할 수 있다 |

## Day6 (10/26) · 머신러닝 첫걸음 — 회귀와 분류

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| 머신러닝 | 데이터 분포 P(X, y)에서 뽑은 표본으로 기대 손실이 작은 함수 f를 찾는 일이다. 규칙 기반보다 유연하지만, 학습 분포와 운영 분포가 다르면(분포 이동) 성능 보장이 깨진다 |
| 특성(Feature) | 예측 시점에 **알 수 있는** 정보만 특성이 될 수 있다. `elapsed_ms`처럼 결과 이후에 생기는 값은 상관이 높아 점수를 올리지만 운영에서는 존재하지 않으므로 누수다. 특성 설계는 모델 선택보다 성능에 더 큰 영향을 주는 경우가 많다 |
| 정답(Label/Target) | 같은 표라도 무엇을 y로 두느냐가 문제 유형(회귀/분류)과 손실 함수, 평가지표를 모두 결정한다. 레이블에 잡음이 많으면 어떤 모델도 그 잡음 이상으로 정확해질 수 없다 |
| 학습(fit) | 손실 함수를 최소화하는 파라미터를 찾는 최적화 문제다. 선형회귀처럼 닫힌 해가 있는 경우도 있고, 신경망처럼 반복 최적화가 필요한 경우도 있다. train 손실 최소화가 목표가 아니라 **일반화 오차** 최소화가 목표다 |
| 예측(predict) | 학습된 파라미터로 하는 순수 계산(추론)이다. 학습 때의 전처리(스케일러 등)를 **같은 값으로** 다시 적용해야 하므로, 전처리와 모델을 한 객체(Pipeline)로 묶는 게 안전하다 |
| 회귀 | 연속값 예측. 손실 선택이 곧 무엇을 예측하는지를 정한다: MSE를 최소화하면 조건부 평균, MAE를 최소화하면 조건부 중앙값을 추정한다 |
| 분류 | 범주 예측. 대부분의 모델은 점수나 확률을 내고, 임계값이 이를 판정으로 바꾼다. 그래서 "모델 품질(확률)"과 "판정 정책(임계값)"을 분리해 평가할 수 있다 |
| 선형회귀 | 최소제곱법은 오차가 정규분포일 때 최대우도 추정과 같다. 계수가 곧 해석(특성 1 증가당 y 변화량)이라 설명력이 높지만, 비선형 관계와 특성 간 상호작용은 직접 만들어 넣지 않으면 표현하지 못한다 |
| 오차 | 오차 = 편향(모델이 체계적으로 빗나감) + 분산(데이터에 따라 흔들림) + 줄일 수 없는 잡음으로 나눠 볼 수 있다. 단순한 모델은 편향이, 복잡한 모델은 분산이 크다(편향-분산 트레이드오프) |
| MAE | 이상치에 강건하고 단위가 원래와 같아 해석이 쉽다. 대신 0에서 미분이 불연속이라 경사 기반 최적화에서는 MSE보다 다루기 불편하다 |
| MSE | 제곱 때문에 큰 오차를 크게 벌한다. 큰 실수 한 번이 치명적인 문제에 맞고, 매끄럽게 미분돼 최적화가 쉽다. 대신 이상치 몇 개가 전체 점수를 지배한다 |
| 로지스틱 회귀 | 로그 오즈 log(p/(1−p))를 선형으로 모델링한다. 출력이 확률로 해석되고 계수가 오즈비로 해석돼 설명력이 높다. 결정 경계가 직선(초평면)이라는 한계가 있다 |
| 임계값 | 정밀도와 재현율을 맞바꾸는 손잡이다. 0.5는 FP와 FN의 비용이 같을 때만 합리적이다. 비용이 다르면 기대 비용을 최소화하는 지점을 valid에서 정한다 |
| KNN | "가까운 점은 비슷한 답을 가진다"는 가정만 쓰는 비모수 방법이다. 학습 비용은 0이지만 예측마다 전체 데이터와 거리를 계산해야 해서 느리다. 차원이 높아지면 모든 점 사이의 거리가 비슷해져 성능이 떨어진다(차원의 저주) |
| K | 작은 K는 저편향·고분산(잡음에 민감), 큰 K는 고편향·저분산(경계가 뭉개짐)이다. 이진 분류에서 동점을 피하려고 보통 홀수를 쓰고, CV로 고른다 |
| 스케일링 | 거리·내적·경사하강법을 쓰는 모델(KNN, 선형, 신경망)에서는 단위가 큰 특성이 결과를 지배하므로 필요하다. 트리 모델은 순서만 보므로 스케일에 영향받지 않는다. 통계량을 train에서만 구하는 이유는 test를 "처음 보는 데이터"로 유지하기 위해서다 |
| train / valid / test | 데이터가 작으면 분할에 따라 점수가 크게 흔들리므로 CV로 보완한다. 불균형 데이터면 층화 분할로 클래스 비율을 유지하고, 시계열이면 무작위가 아니라 시간순으로 나눈다 |
| 데이터 누수 | 학습 시점에 알 수 없어야 할 정보가 학습에 섞이는 것이다. 종류는 ① 특성 누수(결과 이후 값) ② 전처리 누수(전체 통계량 사용) ③ 분할 누수(같은 사용자·중복 행이 train/test에 동시에 존재)가 있다. 점수가 "너무 좋으면" 먼저 의심한다 |

## Day7 (10/27) · 나무 모델 — Decision Tree · Random Forest · XGBoost

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| 결정 트리 | 지니 불순도나 엔트로피를 가장 많이 줄이는 분할을 탐욕적으로 고른다. 스케일링이 필요 없고 비선형·상호작용을 자동으로 잡으며 규칙으로 읽을 수 있다. 대신 데이터가 조금만 바뀌어도 나무 모양이 크게 바뀐다(고분산) |
| 깊이(depth) | 모델 복잡도를 직접 조절하는 하이퍼파라미터다. 깊이 d면 최대 2^d개 영역으로 나뉘어, 깊어질수록 편향↓ 분산↑이다 |
| 잎(leaf) | 잎의 예측은 그 영역 학습 데이터의 평균(회귀)이나 비율(분류)이다. 최소 잎 크기를 키우면 각 예측이 더 많은 표본의 평균이 되어 안정적이지만 세밀함을 잃는다. 깊이 제한과 같은 목적의 다른 손잡이다 |
| 과적합 | 모델이 신호뿐 아니라 train의 잡음까지 외운 상태다. train-valid 간격으로 진단하고, 복잡도 제한·규제·데이터 추가·앙상블로 대응한다 |
| 과소적합 | 모델이 신호조차 표현하지 못하는 상태(고편향)다. 데이터를 더 모아도 해결되지 않으니 모델 용량을 키우거나 특성을 추가해야 한다. 과적합과 처방이 반대라서 둘을 구분하는 게 중요하다 |
| 랜덤 포레스트 | 배깅(부트스트랩 + 평균)으로 분산을 줄이고, 분할마다 특성 일부만 후보로 써서 나무 간 상관을 낮춘다. 평균의 분산은 상관이 낮을수록 더 줄어들기 때문이다. 튜닝 없이도 강하지만 단일 트리의 해석력은 잃는다 |
| 앙상블 | 오류가 서로 독립적일수록 효과가 크다. 같은 실수를 하는 모델을 여러 개 합치면 나아지지 않는다. 배깅은 분산을 줄이고, 부스팅은 편향을 줄인다 |
| XGBoost (부스팅) | 손실의 기울기(잔차) 방향으로 얕은 나무를 순차적으로 더하는 경사 부스팅에 규제항과 2차 미분 정보를 더한 구현이다. 표 데이터에서 보통 가장 강하지만 하이퍼파라미터가 많고, 순차 학습이라 과적합 위험이 있어 학습률·조기 종료가 필요하다 |
| 특성 중요도 | MDI는 train 데이터 기준이라 과적합된 분할도 중요하다고 계산하고, 값의 종류가 많은(고카디널리티) 특성을 과대평가하는 편향이 있다. 빠르지만 참고용이다 |
| 순열 중요도 | 모델에 상관없이 valid 점수 하락으로 재므로 MDI보다 일반화 관점에 가깝다. 대신 상관된 특성이 있으면 하나를 섞어도 다른 특성이 대신해서 둘 다 낮게 나온다. 중요도는 "모델이 의존하는 정도"이지 인과관계가 아니다 |
| 교차검증(CV) | 모든 데이터를 한 번씩 평가에 써서 분할 운에 따른 분산을 줄인다. 평균과 함께 표준편차를 보고해야 차이가 의미 있는지 판단할 수 있다. 비용은 학습을 k번 해야 한다는 것이다 |
| 원핫 인코딩 | 범주에 가짜 순서(qa=1, summary=2)를 부여하지 않기 위해 쓴다. 범주 수가 많으면 열이 폭증하고 희소해지므로, 그때는 빈도·타깃 인코딩이나 임베딩을 고려한다(타깃 인코딩은 누수 주의) |
| 결측값 대체 | 평균 대체는 분산을 줄이고 결측 자체가 가진 정보를 지운다. "결측이었음" 표시 열을 함께 넣으면 그 정보를 보존할 수 있다. 결측이 무작위가 아니라면 대체 방식이 결과를 편향시킨다 |
| Pipeline | 전처리를 모델의 일부로 취급해 fit/predict 경계를 코드 구조로 강제한다. CV 안에서 fold마다 전처리를 다시 학습하므로 전처리 누수를 사람의 주의력이 아니라 구조로 막는다 |
| seed (재현성) | 결과 비교의 공정성을 위한 것이다. seed 하나의 결과는 그 seed에서의 운일 수 있으므로, 중요한 결론은 여러 seed에서 확인한다 |

## Day8 (10/28) · 평가지표와 군집

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| 혼동행렬 | 모든 이진 분류 지표의 원천 데이터다. 지표 하나는 정보를 압축하면서 손실을 일으키므로, 보고할 때는 원본인 혼동행렬을 함께 붙인다 |
| 정확도(Accuracy) | 클래스가 균형이고 오류 비용이 같을 때만 의미가 있다. 불균형 데이터에서는 다수 클래스만 맞혀도 높게 나오므로 기준선(다수 클래스 비율)과 비교해야 한다 |
| 정밀도(Precision) | "양성이라 했을 때 믿을 수 있나". 거짓 경보(FP)가 비쌀 때(스팸 필터가 정상 메일을 버림) 중시한다 |
| 재현율(Recall) | "진짜 양성을 얼마나 놓치지 않나". 놓침(FN)이 비쌀 때(질병, 장애) 중시한다. 임계값을 낮추면 재현율↑ 정밀도↓로, 둘은 같은 손잡이의 양쪽이다 |
| F1 | 정밀도와 재현율의 조화평균이라 둘 중 낮은 쪽에 끌려간다. 둘의 중요도가 같다고 가정한 지표이므로, 비용이 비대칭이면 Fβ나 비용 기반 지표가 더 맞다. TN을 전혀 쓰지 않는다는 점도 한계다 |
| ROC 곡선 | 모든 임계값에서의 (FPR, TPR)을 한 그림에 담아 임계값 선택과 모델 비교를 분리한다. 양성이 매우 드물면 FPR이 작게 보여 낙관적이므로, 그때는 PR 곡선이 더 정보가 많다 |
| AUC | "무작위 양성 하나가 무작위 음성 하나보다 높은 점수를 받을 확률"이다. 순위만 보므로 확률의 보정(calibration)이 엉망이어도 높을 수 있고, 실제로 쓸 임계값 근처의 성능은 알려 주지 않는다 |
| RMSE | MSE와 순위는 같고 단위만 원래대로 돌아온다. MAE보다 항상 크거나 같으며, 둘의 차이가 크면 큰 오차가 소수 섞여 있다는 신호다 |
| 비지도 학습 | 정답이 없으니 "좋은 결과"의 기준을 사람이 정해야 한다. 실루엣 점수 같은 내부 지표는 군집의 모양만 평가하지 업무상 유용성은 보장하지 않는다 |
| K-Means 군집 | 군집 내 제곱거리 합을 최소화한다. 군집이 둥글고 크기가 비슷하다고 가정해서 길쭉하거나 밀도가 다른 군집은 잘 못 찾는다. 초기 중심에 따라 지역 최솟값에 빠지므로 여러 번 초기화(k-means++)한다. 거리 기반이라 스케일링이 필수다 |
| 군집 번호 | 번호는 임의의 이름이라 실행마다 바뀔 수 있다(레이블 교환 문제). 실행 간 비교는 번호가 아니라 중심 좌표나 구성원 겹침으로 해야 한다 |
| 평가 계획 | 결과를 본 뒤 지표를 고르면 유리한 지표를 고르는 편향이 생긴다(사후 선택). 사전 등록은 분석의 자유도를 줄여 결론의 신뢰도를 높인다 |

## Day9 (10/29) · 딥러닝 기초 — Tensor · Autograd · ANN

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| Tensor | 다차원 배열에 device 정보와 계산 그래프 추적 기능을 더한 것이다. NumPy 배열과 달리 GPU에서 연산하고 미분할 수 있다 |
| 기울기(Gradient) | 다변수 함수에서 가장 가파르게 증가하는 방향 벡터다. 국소 정보일 뿐이라 큰 걸음에서는 맞지 않고, 기울기가 0인 곳이 최솟값이 아니라 안장점일 수도 있다 |
| Autograd | 연쇄 법칙을 계산 그래프에 역방향으로 적용하는 역전파 자동 미분이다. 출력이 하나(손실)이고 입력이 많을 때 역방향이 순방향보다 훨씬 효율적이다. 대신 순전파의 중간값을 저장해야 해서 메모리를 많이 쓴다 |
| 경사하강법 | 1차 정보만 쓰는 가장 단순한 최적화다. 뉴턴법 같은 2차 방법은 수렴이 빠르지만 파라미터 수 n에 대해 n² 크기의 헤세 행렬이 필요해 신경망에서는 비현실적이다 |
| 학습률 | 가장 중요한 하이퍼파라미터다. 손실 곡면의 곡률보다 크면 발산한다. 고정값 대신 워밍업이나 점점 줄이는 스케줄을 쓰면 초반 안정성과 후반 미세 조정을 둘 다 얻는다 |
| 인공신경망(ANN) | 비선형 층을 합성한 함수로, 은닉층이 충분히 넓으면 연속함수를 근사할 수 있다(보편 근사 정리). 하지만 "표현할 수 있다"와 "학습으로 찾아낼 수 있다"는 다른 문제다. 표 데이터에서는 부스팅 트리보다 못한 경우가 많다 |
| 가중치 / 편향 | 파라미터 수는 표현력과 과적합 위험, 메모리를 함께 결정한다. 초기값이 모두 같으면 뉴런들이 같은 기울기를 받아 대칭이 깨지지 않으므로 무작위로 초기화한다(Xavier/He) |
| 활성화 함수(ReLU) | 시그모이드·tanh는 양 끝에서 기울기가 0에 가까워 깊은 층에서 기울기가 사라진다. ReLU는 양수 구간 기울기가 1이라 이를 완화하고 계산도 싸다. 대신 음수 입력만 받는 뉴런은 영구히 죽을 수 있어(Dying ReLU) LeakyReLU·GELU 같은 변형을 쓴다 |
| 손실 함수 | 손실은 최적화 대상이고 지표는 평가 대상이라, 서로 다를 수 있다(F1은 미분이 안 돼 직접 최적화하기 어려움). 분류에서 교차 엔트로피를 쓰는 이유는 최대우도와 같고, 시그모이드·softmax와 결합하면 기울기가 단순해지기 때문이다 |
| 배치 | 미니배치는 전체 기울기의 잡음 섞인 추정치다. 이 잡음이 날카로운 최솟값에서 빠져나오게 도와 일반화에 이로울 수 있다. 배치를 키우면 GPU 효율↑ 잡음↓이지만 학습률도 함께 조정해야 한다 |
| 에폭(Epoch) | 에폭 수 자체보다 "가중치 업데이트 횟수"가 학습량을 정한다. 배치 크기를 바꾸면 같은 에폭에서 업데이트 횟수가 바뀌므로, 실험을 비교할 때 둘을 함께 적는다 |
| 학습 루프 | PyTorch는 기울기를 **누적**하는 설계다. 그래서 큰 배치를 여러 번에 나눠 계산하는 기울기 누적이 가능하지만, 대신 매 단계 `zero_grad()`를 직접 불러야 한다 |
| 체크포인트 | `state_dict`(가중치)만 저장하면 코드 구조가 바뀌어도 불러오기 쉽다. 학습을 이어서 하려면 옵티마이저 상태·에폭·seed까지 함께 저장해야 같은 궤적을 재현할 수 있다 |

## Day10 (10/30) · 학습 안정화

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| 옵티마이저 | Adam은 기울기의 1차 모멘트(평균)와 2차 모멘트(제곱 평균)로 파라미터마다 학습률을 조정해 튜닝 없이도 빠르게 수렴한다. 대신 SGD+모멘텀이 일반화가 더 좋은 경우가 보고되며, 가중치 감쇠는 AdamW처럼 분리해야 제대로 작동한다 |
| 모멘텀 | 기울기의 지수 이동 평균으로, 좁은 골짜기에서 진동하는 방향은 상쇄하고 일관된 방향은 누적한다. 관성 때문에 최솟값을 지나칠 수도 있다 |
| 학습 곡선 | 과적합·과소적합·학습률 문제를 진단하는 가장 싼 도구다. train/valid 간격은 분산을, 둘 다 높은 수준은 편향을 보여 준다. 손실과 함께 실제 지표 곡선도 봐야 한다 |
| 배치 크기 | 작은 배치는 잡음이 규제 효과를 주지만 GPU를 덜 쓰고, 큰 배치는 빠르지만 일반화가 나빠질 수 있다. 바꿀 때는 학습률을 함께 조정한다(선형 스케일링 규칙) |
| 모델 너비 | 너비(뉴런 수)와 깊이(층 수)는 다른 축이다. 깊이는 계층적 특징을 효율적으로 표현하고, 너비는 최적화를 쉽게 만든다. 용량을 키우면 규제나 데이터가 함께 늘어야 한다 |
| 드롭아웃 | 매 단계 다른 부분 네트워크를 학습시켜 여러 모델의 앙상블처럼 동작하게 하고, 특정 뉴런에 의존하는 공적응을 막는다. 평가 때 출력 크기를 맞추기 위해 학습 때 1/(1−p)배로 키운다. 학습은 느려진다 |
| 배치 정규화 | 층 입력의 분포를 안정시켜 더 큰 학습률을 쓰게 하고 초기화에 덜 민감하게 만든다. 배치 통계에 의존해서 배치가 작으면 불안정하므로, 시퀀스나 작은 배치에서는 Layer Norm을 쓴다 |
| train 모드 / eval 모드 | 드롭아웃과 배치 정규화는 학습과 추론에서 다르게 동작해야 한다. `eval()`을 빼먹으면 추론 결과가 매번 달라지고 성능이 떨어지는데, 에러가 나지 않아 발견하기 어렵다. `torch.no_grad()`는 기울기 계산만 끄는 별개의 기능이다 |
| 최적 상태 복원 | 조기 종료의 일종이다. valid로 학습 길이를 고르므로 valid 점수는 약간 낙관적이 된다. 그래서 최종 보고는 test로 한다 |

## Day11 (11/2) · CNN · 이미지 분류 · 전이학습

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| 이미지 텐서 | PyTorch는 채널 우선(C, H, W), OpenCV·PIL은 채널 마지막(H, W, C)을 쓴다. 값 범위를 0~1로 바꾼 뒤 사전학습 모델이 학습한 평균·표준편차로 정규화해야 그 모델이 본 입력 분포와 같아진다 |
| 합성곱(Convolution) | 같은 필터를 모든 위치에 공유하므로(가중치 공유) 완전연결층보다 파라미터가 훨씬 적고, 물체가 어디에 있든 같은 특징을 찾는다(이동 등변성). 이 "가까운 픽셀끼리 관련 있다"는 귀납 편향 덕분에 적은 데이터로도 잘 배운다. 대신 멀리 떨어진 위치 간 관계는 층을 많이 쌓아야 본다 |
| 필터(커널) | 사람이 설계하던 엣지 필터를 데이터에서 학습한다. 앞쪽 층은 엣지·색, 뒤쪽 층은 부분·물체처럼 점점 추상적인 특징을 배운다. 3×3을 여러 번 쌓으면 큰 필터 하나보다 적은 파라미터로 같은 범위를 보면서 비선형성은 더 많이 넣을 수 있다 |
| 채널 | 출력 채널 수 = 학습할 특징의 종류 수다. `Conv2d(3,16,3)`의 파라미터는 16×3×3×3 + 16 = 448개로, 입력 크기(64×64)와 무관하다 |
| 풀링 | 해상도를 줄여 계산량을 줄이고 작은 위치 변화에 둔감하게(이동 불변성) 만든다. 대신 정확한 위치 정보를 버리므로 탐지·분할에서는 조심해서 쓴다. 요즘은 stride 2 합성곱으로 대체하기도 한다 |
| CNN | 계층적 특징 추출 + 분류기 구조다. 마지막에 flatten 대신 Global Average Pooling을 쓰면 파라미터가 줄고 입력 크기에 덜 묶인다 |
| ImageFolder | 폴더 구조가 곧 레이블이라 간편하지만, 클래스 번호가 알파벳 순서로 정해진다. 학습 때의 `class_to_idx`를 저장하지 않으면 추론 때 번호가 어긋날 수 있다 |
| 데이터 증강 | "이 변환을 해도 정답은 그대로다"라는 사전 지식을 데이터로 주입하는 규제다. 정답을 바꾸는 증강(숫자 6을 180° 회전 → 9)은 오히려 해롭다. valid/test에 적용하지 않는 이유는 실제 입력 분포에서 평가해야 하기 때문이다 |
| 전이학습 | 대규모 데이터에서 배운 일반 특징을 재사용해, 데이터가 적어도 과적합을 줄이고 수렴을 빠르게 한다. 원천 도메인(자연 사진)과 목표 도메인(의료 영상)이 멀수록 효과가 줄어든다 |
| 사전학습 가중치 | 모델 구조와 함께 **전처리 규칙**(입력 크기, 정규화 값)도 가져와야 한다. 라이선스와 학습 데이터의 편향도 함께 상속된다는 점에 주의한다 |
| 동결(Freeze) | 데이터가 적을수록 많이 동결해 과적합을 막고, 많을수록 더 풀어 도메인에 맞춘다. 동결하면 역전파 계산과 옵티마이저 메모리가 줄어든다 |
| 벤치마크 | 첫 실행에는 메모리 할당, 커널 선택, 지연 로딩 비용이 섞여 있다. GPU는 비동기로 실행되므로 `torch.cuda.synchronize()` 없이 시간을 재면 실제보다 짧게 나온다. 평균과 함께 p50·p95를 보고해야 꼬리 지연을 알 수 있다 |

## Day12 (11/3) · 순서가 있는 데이터 — RNN · LSTM · Attention

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| 시퀀스 | 순서가 정보인 데이터다. 순서를 무시하는 모델(평균, bag-of-words)은 단순하고 빠르지만 "A가 B를 이겼다"와 "B가 A를 이겼다"를 구분하지 못한다 |
| 시계열 | 관측값이 서로 독립이 아니라(자기상관) 일반적인 i.i.d. 가정이 깨진다. 그래서 무작위 분할·일반 CV를 쓰면 미래 정보가 과거 학습에 섞여 낙관적인 점수가 나온다 |
| Window | 고정 길이 과거로 다음 값을 예측하는 지도학습 문제로 바꾼다. 창이 짧으면 긴 주기를 놓치고, 길면 표본 수가 줄고 계산이 늘어난다 |
| 시간순 분할 | 운영 상황(과거로 학습 → 미래 예측)을 그대로 흉내 낸다. 분할 후에 Window를 만들어야 경계를 걸친 창이 train과 test에 동시에 들어가는 누수를 막는다 |
| Padding | 텐서는 직사각형이어야 하므로 길이를 맞춘다. 가장 긴 것에 맞추면 계산이 낭비되므로 비슷한 길이끼리 묶는(bucketing) 방법이 있다. 패딩이 계산에 섞이지 않게 마스크가 반드시 짝으로 필요하다 |
| 마스크 | 패딩을 "값 0"으로 두면 평균과 Attention에 실제로 참여해 결과를 왜곡한다. Attention에서는 softmax 전에 패딩 위치 점수를 −∞로 만들어 가중치를 정확히 0으로 만든다 |
| RNN | 시간마다 같은 가중치를 공유해 길이에 상관없이 처리한다. 역전파할 때 같은 행렬이 계속 곱해져 기울기가 소실되거나 폭발하므로 긴 의존성을 배우기 어렵다. 순차 계산이라 병렬화도 안 된다 |
| LSTM | 셀 상태를 곱셈이 아니라 덧셈으로 갱신하는 경로가 있어 기울기가 오래 살아남는다. RNN보다 파라미터가 약 4배 많다. GRU는 게이트를 줄여 더 가볍고 성능은 비슷한 경우가 많다 |
| Autoencoder | 병목(압축 차원)이 핵심이다. 병목이 너무 넓으면 입력을 그대로 복사하는 법만 배우고, 너무 좁으면 정상 데이터도 복원하지 못한다. 레이블 없이 학습할 수 있다는 것이 장점이다 |
| 재구성 오차 / 이상탐지 | "정상만 잘 복원하도록 배웠으니 처음 보는 패턴은 오차가 크다"는 가정이다. 이상이 학습 데이터에 섞이면 그것도 복원하게 되고, 정상이지만 드문 패턴은 오탐이 된다. 임계값은 허용할 오탐률로 정한다 |
| Attention | 모든 위치 쌍을 직접 연결해 거리와 상관없이 정보를 주고받고 병렬 계산이 된다. 그래서 RNN의 순차성과 장거리 문제를 함께 풀었다(Transformer). 대신 계산과 메모리가 길이의 제곱(n²)으로 늘어난다. Attention 가중치가 그대로 "모델의 설명"이라고 보기는 어렵다 |

## Day13 (11/4) · OpenCV 이미지·영상 전처리

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| OpenCV | C++ 기반이라 빠르고 고전 영상처리 알고리즘이 풍부하다. 실패 시 예외 대신 `None`을 돌려주는 설계라서, 확인하지 않으면 한참 뒤 엉뚱한 곳에서 에러가 난다 |
| BGR | 역사적 관례일 뿐 정보량은 같다. 문제는 라이브러리 간 경계(OpenCV → Matplotlib·PIL·사전학습 모델)에서 변환을 잊으면 색이 바뀐 입력으로 조용히 성능이 떨어진다는 것이다 |
| 그레이스케일 | 색 정보를 버려 데이터와 계산을 1/3로 줄인다. 모양·글자 인식처럼 색이 중요하지 않은 작업에서 유리하고, 색이 단서인 작업(신호등)에서는 정보 손실이다 |
| 리사이즈 | 줄일 때는 `INTER_AREA`(앨리어싱 감소), 키울 때는 `INTER_LINEAR`·`INTER_CUBIC`이 일반적이다. 가로세로 비율을 무시하면 모양이 왜곡되므로 비율 유지 + 패딩(letterbox)을 쓰기도 한다 |
| 블러(필터) | 저역 통과 필터로 고주파 잡음을 줄인다. 하지만 엣지도 고주파라 함께 뭉개진다. 엣지를 보존하려면 중앙값 필터(소금-후추 잡음에 강함)나 양방향 필터를 쓴다 |
| 엣지 검출(Canny) | 가우시안 평활 → 기울기 → 비최대 억제(엣지를 1픽셀로 얇게) → 이중 임계값 연결의 단계로, 잡음 내성과 얇은 엣지를 함께 얻는다. 임계값 두 개를 영상마다 조정해야 하는 것이 단점이다 |
| 이진화(Threshold) | 전역 임계값은 조명이 고르지 않으면 실패한다. Otsu 방법은 히스토그램에서 최적 임계값을 자동으로 찾고, 적응형 임계값은 영역마다 다른 기준을 쓴다 |
| 모폴로지 | 이진 영상에서 모양을 다듬는다. 열기(침식→팽창)는 작은 잡음점을 제거하고, 닫기(팽창→침식)는 작은 구멍을 메운다. 구조 요소 크기가 지울 대상보다 크면 실제 객체도 지워진다 |

## Day14 (11/5) · 전이학습 심화와 오류 분석

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| Dataset / DataLoader | 데이터 접근(Dataset)과 배치 구성·병렬 로딩(DataLoader)을 분리한 설계다. `num_workers`를 늘리면 GPU가 데이터를 기다리는 시간이 줄지만 메모리와 프로세스 비용이 든다. valid/test를 섞지 않는 이유는 결과를 재현하고 예측을 원본 순서와 맞추기 위해서다 |
| 헤드(Head) | 사전학습 몸통은 일반 특징을, 새 헤드는 내 작업을 담당한다. 새 헤드는 무작위 초기화라 초반 기울기가 크다. 그래서 몸통과 동시에 학습하면 좋은 사전학습 특징이 망가질 수 있다 |
| 파인튜닝 | 2단계로 나누는 이유가 바로 위 문제다. 헤드를 먼저 안정시킨 뒤, 몸통은 작은 학습률로 조금만 바꾼다. 층마다 학습률을 다르게 줄 수도 있다. 전부 풀면 표현력은 최대지만 데이터가 적으면 과적합하고 사전 지식을 잊는다(파괴적 망각) |
| 클래스 불균형 | 손실이 다수 클래스에 지배되어 모델이 소수 클래스를 무시해도 손실이 낮다. 대응책은 ① 재표본추출 ② 가중 손실 ③ 임계값 조정 ④ 지표 변경이며, 평가에서는 클래스별 재현율·PR-AUC를 본다 |
| 가중 손실 | 소수 클래스 오류의 비용을 키워 결정 경계를 옮긴다. 데이터를 복제하는 오버샘플링과 효과는 비슷하지만 과적합 위험이 적다. 가중치가 너무 크면 거짓 경보가 늘어나므로 업무 비용에 맞춰 정한다 |
| 오류 분석 | 지표는 "얼마나"를, 오류 분석은 "왜"를 알려 준다. 틀린 사례를 유형별로 세면 데이터 추가·레이블 수정·모델 변경 중 어디에 시간을 쓸지 우선순위가 나온다. 레이블 자체가 틀린 경우도 꽤 많다 |
| Grad-CAM | 클래스 점수를 마지막 합성곱 특징으로 미분해서 "어디를 보고 판단했나"를 시각화한다. 모델이 물체 대신 배경·워터마크를 보는 지름길 학습(shortcut)을 찾는 데 유용하다. 해상도가 낮고, 보여 준 영역이 "인과적 이유"라는 보장은 없다 |

## Day15 (11/6) · 객체 탐지 — IoU · YOLO

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| 객체 탐지 | 분류(무엇) + 회귀(어디)를 동시에 푸는 문제다. 출력 개수가 정해져 있지 않아서 후처리(NMS)와 전용 지표(mAP)가 필요하다. 픽셀 단위로 경계가 필요하면 분할(segmentation)을 쓴다 |
| 바운딩 박스 | 축에 정렬된 직사각형이라 기울어진 물체는 배경을 많이 포함한다. 좌표 형식(xyxy/xywh, 픽셀/정규화)을 혼동하는 것이 가장 흔한 버그이며, 에러 없이 잘못된 위치를 낸다 |
| IoU | 크기에 무관한 겹침 척도다. 작은 물체는 몇 픽셀만 어긋나도 IoU가 크게 떨어져 같은 기준에서 불리하다. 두 상자가 겹치지 않으면 기울기가 0이라 손실로 쓸 때는 GIoU·CIoU 같은 변형을 쓴다 |
| 라벨 파일 | 좌표를 0~1로 정규화하면 이미지 크기를 바꿔도 라벨이 그대로 유효하다. 대신 원본 크기를 알아야 픽셀 좌표로 되돌릴 수 있다 |
| YOLO | 한 번의 순전파로 모든 상자를 예측하는 1단계 탐지기라 실시간이 가능하다. 후보 영역을 먼저 뽑는 2단계 탐지기(Faster R-CNN)보다 전통적으로 작고 밀집한 물체에 약했지만 버전이 오르며 격차가 줄었다 |
| 신뢰도(Confidence) | 임계값을 낮추면 재현율↑ 정밀도↓다. NMS는 같은 물체의 중복 상자를 지우는데, 서로 겹친 다른 물체(군중)까지 지울 수 있어 IoU 기준이 성능에 영향을 준다 |
| mAP50 | 모든 신뢰도 임계값에서의 성능을 요약해 임계값 선택과 무관하게 모델을 비교한다. IoU 0.5는 느슨한 기준이라 위치 정확도를 덜 반영한다. 그래서 0.5~0.95를 평균한 mAP50-95도 함께 본다 |
| 추적(Tracking) | 탐지는 프레임마다 독립이라 ID가 없다. 추적은 운동 모델(칼만 필터)과 겉모습 특징으로 프레임 간 대응을 찾는다. 가림이 생기거나 물체가 교차하면 ID가 바뀌는 오류(ID switch)가 대표적인 실패다 |

## Day16 (11/9) · OCR · VLM · 엣지 추론

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| OCR | 탐지와 인식을 분리한 파이프라인이라 각 단계를 따로 디버깅할 수 있다. 대신 앞 단계 오류가 뒤로 전파된다. 글자 단위 정확도는 높아도 읽는 순서나 표 구조 같은 레이아웃은 별도 문제다 |
| 기울기 보정 | 인식 모델은 대부분 정면의 수평 글자로 학습되어 입력을 그 분포로 맞춰 주는 것이다. 꼭짓점 검출이 실패하면 오히려 왜곡되므로 실패 시 원본을 쓰는 대비책이 필요하다 |
| 필드 추출 | 규칙(정규식)은 빠르고 설명 가능하지만 양식이 바뀌면 깨진다. 모델 기반 추출은 유연하지만 검증이 어렵다. 정해진 양식에는 규칙, 다양한 양식에는 모델이 맞다 |
| VLM | 이미지와 텍스트를 같은 표현 공간에서 다뤄 "질문에 맞춰" 이미지를 해석한다. OCR보다 문맥 이해가 좋지만 느리고 비싸며, 없는 글자를 지어낼 수 있다(할루시네이션) |
| 근거(Evidence) | 추출값의 출처를 남기면 사람이 빠르게 검증하고 오류의 단계를 찾을 수 있다. 신뢰도가 낮은 것만 사람이 검토하게 하면 자동화율과 정확도를 함께 관리할 수 있다 |
| 엣지 추론 | 지연·개인정보·네트워크 의존성을 얻는 대신 정확도를 내준다. 양자화(32비트 → 8비트), 가지치기, 지식 증류로 모델을 줄이며, 줄인 뒤에는 정확도를 다시 측정해야 한다 |
| Hybrid | 싼 방법을 먼저 쓰고 불확실한 경우만 비싼 방법으로 넘기는 계단식 구조다. 넘기는 기준(신뢰도 임계값)이 비용과 정확도의 맞교환 지점이 된다 |

## Day17 (11/10) · FastAPI로 지식 관리 API 만들기

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| API | 구현을 숨기고 계약(입출력 형식)만 공개해서 서버와 클라이언트가 독립적으로 바뀔 수 있게 한다. 한번 공개한 계약은 바꾸기 어려우므로 버전 관리(`/v1/`)가 필요하다 |
| FastAPI | 타입 힌트 하나로 검증·직렬화·문서화를 함께 얻는다. 비동기를 지원해 I/O가 많은 서비스에 유리하다. 단, `async` 함수 안에서 동기 블로킹 호출(무거운 모델 추론, 동기 DB 드라이버)을 하면 서버 전체가 멈춘다 |
| 엔드포인트 | REST에서는 주소가 자원(명사), 메서드가 행위(동사)를 나타낸다. 경로 매개변수는 자원을 식별하고, 쿼리 매개변수(`?category=AI`)는 필터·정렬처럼 선택적인 조건에 쓴다 |
| HTTP 메서드 | GET·PUT·DELETE는 같은 요청을 여러 번 보내도 결과가 같아야 한다(멱등성). POST는 멱등하지 않아 재시도하면 중복 생성될 수 있다. 이 차이가 네트워크 실패 시 안전하게 재시도할 수 있는지를 정한다 |
| CRUD | 대부분의 데이터 서비스의 공통 골격이다. 실제 업무 동작("승인", "취소")은 CRUD로 깔끔하게 표현되지 않아 상태 필드를 수정하거나 별도 행위 엔드포인트로 설계한다 |
| 상태 코드 | 클라이언트가 본문을 해석하지 않고도 성공·실패와 재시도 여부를 판단하게 해 준다. 4xx는 클라이언트 잘못(고쳐서 다시), 5xx는 서버 잘못(나중에 다시)이다. 오류에도 200을 돌려주면 모니터링과 재시도 로직이 망가진다 |
| 입력 검증 | 신뢰 경계(외부 입력이 들어오는 곳)에서 한 번 검증하면 내부 코드는 올바른 형식을 가정할 수 있다. 형식 검증(타입)과 업무 규칙 검증(권한, 중복)은 다른 층이다 |
| 파일 저장(영속성) | JSON 파일은 단순하지만 동시 쓰기, 부분 쓰기(쓰는 도중 장애), 검색 성능에 취약하다. 임시 파일에 쓴 뒤 이름을 바꾸는 원자적 쓰기로 일부를 보완할 수 있다. 규모가 커지면 DB로 옮기는 이유가 바로 이 한계다. ID를 재사용하지 않는 것은 예전 참조가 엉뚱한 새 데이터를 가리키는 것을 막기 위해서다 |

## Day18 (11/11) · PostgreSQL · SQL · ERD

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| 관계형 DB / 테이블 | 데이터를 중복 없이 나눠 저장하고(정규화) 필요할 때 JOIN으로 합친다. 중복이 없으니 수정이 한 곳에서 끝나 불일치가 생기지 않는다. 대신 읽을 때 JOIN 비용이 들어, 읽기가 많은 곳에서는 일부러 중복을 허용(비정규화)하기도 한다 |
| SQL | 선언형 언어라서 "어떻게"는 옵티마이저가 정한다. 같은 쿼리라도 데이터 양과 인덱스에 따라 실행 계획이 바뀌므로, 느릴 때는 쿼리 문장이 아니라 실행 계획을 봐야 한다 |
| SELECT · WHERE · ORDER BY · LIMIT | 실행의 논리적 순서는 FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT이다. 그래서 SELECT에서 지은 별칭을 WHERE에서 쓸 수 없다. ORDER BY 없는 LIMIT은 결과 순서가 보장되지 않는다 |
| 기본키(PK) | 행의 불변 식별자다. 의미 있는 값(이메일)을 PK로 쓰면 그 값이 바뀔 때 참조가 모두 깨지므로, 보통 의미 없는 대리키(id)를 쓰고 업무 키에는 UNIQUE를 건다 |
| 외래키(FK) | 참조 무결성을 DB가 보장해서 애플리케이션 버그가 있어도 고아 데이터가 생기지 않는다. 대신 쓰기마다 검사 비용이 들고, 부모 삭제 시 동작(CASCADE·RESTRICT)을 정해야 한다 |
| JOIN | INNER는 양쪽에 다 있는 행만, LEFT는 왼쪽 행을 모두 남기고 없는 쪽을 NULL로 채운다. 1:N을 JOIN하면 1쪽 행이 N배로 늘어나서, 그 상태로 SUM하면 값이 부풀려지는 실수가 흔하다 |
| 집계(GROUP BY) | 그룹 전 조건은 WHERE, 그룹 후 조건은 HAVING에 쓴다. `COUNT(*)`는 NULL을 포함한 행 수, `COUNT(열)`은 NULL을 뺀 수라 결과가 다를 수 있다 |
| 제약조건 | 규칙을 애플리케이션이 아니라 데이터 옆에 두면, 어떤 프로그램이 쓰든 규칙이 지켜진다. 애플리케이션 검증은 사용자 친화적인 오류 메시지를, DB 제약은 최종 안전망을 맡는다 |
| ERD | 코드 전에 데이터 구조를 합의하는 도구다. 관계의 카디널리티(1:1, 1:N, N:M)가 테이블 구조를 정한다. N:M은 중간 테이블(`order_items`)로 풀어야 한다 |
| 트랜잭션 | ACID(원자성·일관성·고립성·지속성)를 보장한다. 고립 수준을 높이면 동시 실행 이상현상이 줄지만 대기와 충돌이 늘어 처리량이 떨어진다. PostgreSQL 기본값은 Read Committed다 |
| ROLLBACK | 원자성의 구현이다. 여러 단계 중 하나라도 실패하면 전부 되돌려서 "재고는 줄었는데 주문은 없는" 중간 상태가 남지 않게 한다. 이미 COMMIT한 것은 되돌릴 수 없어 백업이 따로 필요하다 |
| 인덱스 | B-tree로 조회를 O(n)에서 O(log n)으로 줄인다. 대신 저장 공간을 쓰고 INSERT·UPDATE마다 인덱스도 갱신해야 해서 쓰기가 느려진다. 선택도가 낮은 열(성별)이나 작은 테이블에서는 옵티마이저가 인덱스를 쓰지 않는 게 오히려 빠르다 |

## Day23 (11/18) · Embedding · pgvector

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| 임베딩 | 의미가 비슷한 입력이 가까워지도록 학습한(대조 학습) 밀집 벡터다. 키워드 검색(BM25)은 단어가 정확히 같아야 하지만 임베딩은 동의어·바꿔 말하기를 잡는다. 반대로 고유명사, 제품 코드, 숫자처럼 정확한 일치가 중요한 경우에는 키워드 검색이 강해서 둘을 섞는 하이브리드 검색을 쓴다 |
| 벡터 / 차원 | 차원이 크면 표현력은 좋지만 저장 공간·검색 시간·메모리가 비례해서 늘어난다. 서로 다른 모델의 벡터는 같은 차원이어도 공간이 달라 비교할 수 없다. 모델을 바꾸면 전체를 다시 임베딩해야 한다 |
| 유사도 | 내적은 방향과 길이를 함께 반영해서, 길이가 큰(긴 문서, 자주 나온 단어) 벡터가 유리해지는 편향이 있다. 무엇을 "비슷하다"로 볼지는 모델이 학습할 때 쓴 유사도를 따라야 한다 |
| 코사인 유사도 | 방향만 비교해 길이 편향을 없앤다. 정규화해 두면 내적·코사인·유클리드 거리의 순위가 모두 같아지므로, 미리 정규화하고 빠른 내적을 쓰는 것이 일반적이다 |
| E5 모델 | 질문과 문서는 길이와 문체가 다른 비대칭 검색이라 `query:`·`passage:` 접두어로 역할을 구분해서 학습했다. 접두어를 빼거나 바꾸면 에러 없이 성능만 떨어진다. 모델 카드의 사용 규칙이 곧 계약이다 |
| pgvector | 벡터를 업무 데이터와 같은 DB에 두어 JOIN·필터·트랜잭션을 함께 쓴다. 운영할 시스템이 하나 줄어든다. 수억 건 이상이거나 아주 낮은 지연이 필요하면 전용 벡터 DB가 유리할 수 있다. 연산자(`<=>` 코사인, `<->` L2, `<#>` 음의 내적)를 인덱스 종류와 맞춰야 인덱스를 쓴다 |
| Top-k 검색 | k가 크면 재현율↑이지만 뒤 단계(리랭킹, LLM Context)의 비용과 잡음이 늘어난다. 그래서 1단계는 넉넉한 k, 2단계에서 줄이는 구조가 나온다 |
| HNSW 인덱스 | 근사 최근접 이웃(ANN) 검색이다. 정확도(재현율) 일부를 내주고 속도를 얻는다. `m`·`ef_construction`(구축)과 `ef_search`(검색)로 정확도-속도-메모리를 조절한다. IVFFlat보다 보통 정확하고 빠르지만 메모리와 구축 시간이 더 든다. WHERE 필터와 함께 쓰면 결과가 k개보다 적게 나올 수 있다 |
| 관련성 평가 | "검색이 좋아졌다"를 감이 아니라 숫자로 비교하기 위한 기준이다. 정답 레이블을 만드는 비용이 크고, 레이블이 불완전하면(정답인데 표시가 없음) 좋은 검색이 오히려 낮은 점수를 받는다 |
| Retriever | 검색 방식(벡터·키워드·하이브리드)을 같은 인터페이스 뒤에 숨겨서 RAG 나머지 부분을 바꾸지 않고 교체·비교할 수 있게 한다 |

## Day24 (11/19) · 문서 파싱 · 청킹 · 인덱싱

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| 수집(Collection) | 데이터 계보(lineage)의 시작점이다. "이 답이 어느 파일의 어느 버전에서 왔나"를 거꾸로 추적하려면 수집 시점에 기록해 둬야 한다. 나중에 복원하기는 거의 불가능하다 |
| 해시(SHA-256) | 내용 기반 식별자라 파일 이름이나 수정 시각이 바뀌어도 같은 내용을 알아본다. 증분 처리(바뀐 것만 다시 처리)와 중복 제거의 기반이다. 1바이트만 달라도 완전히 다른 값이 나와서 "거의 같은" 문서는 찾지 못한다 |
| 파싱 | 형식마다 실패 방식이 다르다. PDF는 글자 순서·표·다단 편집이 깨지고, HTML은 메뉴·광고 같은 잡음이 섞이며, 스캔본은 OCR 오류가 생긴다. 파싱 품질이 검색 품질의 상한을 정하므로(쓰레기가 들어가면 쓰레기가 나온다) 파싱 결과를 샘플로 눈으로 확인해야 한다 |
| 정제(Cleaning) | 같은 내용이 다른 바이트가 되는 것을 막아 해시·중복 제거·검색 일치를 안정시킨다. 너무 공격적으로 정제하면 의미 있는 정보(표의 줄바꿈, 코드 들여쓰기)를 잃으므로 무엇을 바꿨는지 기록한다 |
| 유니코드 정규화(NFC/NFKC) | macOS 파일 이름은 한글을 자모로 분해(NFD)해 저장하는 경우가 있어, 눈으로는 같아도 문자열 비교·검색이 실패한다. NFC는 의미를 보존하고, NFKC는 더 공격적으로 통일하는 대신 원래 모양 정보를 잃는다. 질문과 문서에 **같은** 정규화를 적용하는 것이 핵심이다 |
| 청킹(Chunking) | 임베딩 모델의 입력 길이 한도와 검색 정밀도 때문에 나눈다. 고정 길이 분할은 단순하지만 문장·문단 중간을 자르고, 구조 기반(제목·문단) 분할은 의미 단위를 지키지만 조각 크기가 들쭉날쭉하다 |
| Chunk Size / Overlap | 작은 조각은 검색 정밀도↑ 문맥↓, 큰 조각은 문맥↑이지만 여러 주제가 섞여 벡터가 흐려진다. 겹침은 경계 손실을 줄이지만 저장 공간이 늘고 같은 내용이 중복 검색된다. 정답은 없고 Gold 데이터셋으로 측정해서 정한다 |
| Offset | 조각과 원문의 연결을 보존해 인용 위치를 정확히 표시하고, 정제·청킹 단계가 내용을 바꾸지 않았는지 기계적으로 검증할 수 있게 한다 |
| 토큰 / 토크나이저 | 모델의 한도는 글자 수가 아니라 토큰 수다. 한국어는 영어보다 같은 의미에 토큰이 더 많이 드는 경우가 많다. 한도를 넘는 부분은 에러 없이 잘려서(truncation) 조각 뒷부분이 검색에서 조용히 사라진다 |
| 검증(Coverage·Gap) | 청킹 버그(조각 누락, 경계 계산 실수)는 검색 결과에서는 거의 드러나지 않는다. 그래서 인덱싱 전에 불변 조건(전체를 덮는다, 원문과 일치한다)을 기계적으로 확인한다 |
| 격리(Quarantine) | 실패 하나 때문에 전체 파이프라인을 멈추지도, 조용히 버리지도 않는 중간 방식이다. 처리량은 유지하면서 실패를 눈에 보이게 남긴다. 격리 목록을 아무도 안 보면 데이터가 조용히 빠지는 것과 같아지므로 개수를 보고서에 포함한다 |
| 메타데이터 | 필터(권한, 날짜, 문서 종류)로 검색 범위를 좁혀 정확도와 보안을 함께 얻는다. 특히 접근 권한 필터는 검색 단계에서 걸어야 한다. LLM에게 "보여 주지 마"라고 하는 것은 보안이 아니다 |
| 인용(Citation) | 사용자가 답을 검증하게 해 주고, 평가 때 근거 일치(Faithfulness)를 측정하는 기준점이 된다. 모델이 출력한 인용 번호가 실제 검색 결과에 있는지는 코드로 따로 확인해야 한다 |
| 인덱싱 | Stage → 검증 → Publish(원자적 교체)는 배포의 블루-그린 방식과 같은 원리다. 사용자는 항상 완전한 한 버전만 보고, 문제가 생기면 이전 버전으로 즉시 되돌릴 수 있다. 대신 교체하는 동안 저장 공간이 두 배로 든다 |
| Ingestion 파이프라인 | 멱등성(다시 실행해도 같은 결과)이 있어야 실패 후 안전하게 재실행하고, 결과 차이가 "입력이 바뀌어서"인지 판단할 수 있다. 단계별 개수 보고서가 있으면 어느 단계에서 데이터가 빠졌는지 바로 찾는다 |

## Day25 (11/20) · 개인 프로젝트 — 보고서 처리 Agent

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| 요구사항 명세서(SRS) | "완료"의 기준을 미리 합의해서 범위가 계속 늘어나는 것(scope creep)과 "다 됐다/안 됐다" 논쟁을 막는다. 완료 조건은 테스트할 수 있게 써야 한다("빠르게" ✗ → "1초 이내" ✓). 너무 자세하면 변경 비용이 커진다 |
| ERD → API → JSON | 바깥(데이터)에서 안쪽(형식)으로 결정을 좁혀, 뒤 단계에서 앞 결정을 뒤집는 비용을 줄인다. 데이터 모델은 바꾸기 가장 어려우므로 먼저 정한다 |
| API 계약 | 계약이 먼저 있으면 프론트엔드·백엔드·테스트를 병렬로 만들 수 있다(계약 우선 설계). OpenAPI 스키마로 쓰면 문서·검증·목(mock) 서버를 자동 생성할 수 있다 |
| 완료 체크리스트 | 예상 결과를 실행 **전에** 적어 두면, 결과를 본 뒤 기준을 맞춰 버리는 확증 편향을 막는다 |
| 추적성 | 요구사항이 바뀌었을 때 영향받는 코드와 테스트를 바로 찾는다. 빠진 요구사항(테스트 없음)과 불필요한 코드(요구사항 없음)가 함께 드러난다. 유지 비용이 있어 규모가 커지면 도구로 자동화한다 |
| Agent | LLM이 다음 행동을 스스로 고르는 반복 루프다. 고정 파이프라인보다 유연하지만 경로가 매번 달라 테스트·비용 예측·디버깅이 어렵다. 그래서 상태 기록(trace), 반복 횟수 제한, 도구 권한 제한이 필수다. 단계가 정해져 있으면 Agent보다 고정 워크플로가 더 안전하고 싸다 |

## Day26 (11/23) · Basic RAG & LangChain

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| LLM | 다음 토큰 확률을 학습한 언어 모델이라 지식이 파라미터에 압축돼 있다. 지식을 업데이트하려면 재학습(비쌈)이 필요하고, 어떤 지식이 어디서 왔는지 출처를 댈 수 없다. RAG가 이 두 한계를 푸는 방법이다 |
| 할루시네이션 | 모델은 "그럴듯함"을 최적화하지 "사실"을 최적화하지 않는다. 근거를 주면(RAG) 줄어들지만 없어지지는 않는다. 그래서 근거 일치를 따로 검증하고, 모를 때 "모른다"고 답하는 경로를 설계해야 한다 |
| RAG | 지식(문서)과 추론(LLM)을 분리한다. 문서만 바꾸면 지식이 갱신되고 출처를 댈 수 있으며, 재학습보다 싸다. 대신 답의 품질 상한이 검색 품질로 정해진다. 검색이 틀리면 LLM은 틀린 근거로 그럴듯하게 답한다. 문체·형식을 바꾸는 것이 목적이라면 RAG가 아니라 파인튜닝이 맞다 |
| Hit | 검색 결과의 최소 단위다. 점수는 검색 방식마다 척도가 달라(코사인 거리 vs 리랭커 점수) 서로 다른 검색기의 점수를 그대로 비교하거나 합치면 안 된다 |
| Context | 많이 넣으면 재현율↑이지만 비용·지연이 늘고, 관련 없는 내용이 섞여 모델이 헷갈린다. 긴 Context 중간에 있는 정보를 놓치는 현상(lost in the middle)도 있다. 그래서 적고 정확한 Context가 많고 흐릿한 Context보다 낫다 |
| LangChain | 부품을 공통 인터페이스로 감싸 교체와 조합이 쉽다. 대신 추상화 층이 늘어 디버깅할 때 실제로 어떤 프롬프트가 나갔는지 보기 어렵고, 라이브러리 버전 변화가 빠르다. 단순한 경우에는 SDK를 직접 호출하는 게 더 명확할 수 있다 |
| Prompt 템플릿 | 고정 지시와 변하는 입력을 분리해서 프롬프트를 버전 관리하고 테스트할 수 있게 한다. 문서 안에 "이전 지시를 무시하라" 같은 문장이 있으면 지시로 오해될 수 있으므로(프롬프트 인젝션), 문서를 명확한 구분자로 감싸고 "데이터일 뿐"이라고 명시한다 |
| Chat Model | 역할 구분은 모델이 지시(system)와 데이터(user, 문서)의 우선순위를 다르게 보도록 학습된 관례다. temperature가 낮으면 일관되고 재현 가능하지만 다양성이 줄어든다. 평가·추출 작업에는 낮게 둔다. 0이어도 완전히 결정적이라는 보장은 없다 |
| Runnable / invoke | 모든 부품이 같은 인터페이스(`invoke`·`batch`·`stream`)를 가지므로 조합해도 같은 인터페이스가 된다(합성 가능성). 그래서 평가 코드가 체인 내부를 몰라도 실행할 수 있다 |
| Chain | 선언적으로 연결하면 흐름이 한눈에 보이고 배치·스트리밍·재시도를 공짜로 얻는다. 분기·반복이 많아지면 파이프 표기로는 표현이 어려워 그래프 기반 도구(LangGraph)로 넘어간다 |
| Structured Output | 자유 텍스트를 파싱하는 취약한 코드를 없앤다. JSON 스키마나 함수 호출 기능을 쓰면 형식 오류가 크게 줄지만, 형식이 맞아도 **내용**이 맞다는 보장은 없다 |
| Validation | LLM 출력은 신뢰할 수 없는 외부 입력처럼 다뤄야 한다. 형식 검증은 싸고 확실하다. 근거 검증(인용이 실제 Hit에 있나)은 지어낸 출처를 잡는다. 실패 시 조용히 넘어가지 않고 "모름"을 돌려주면 정확도는 약간 떨어져도 신뢰도는 올라간다 |
| RAG API | 체인을 HTTP 뒤에 두면 호출하는 쪽은 내부를 몰라도 된다. LLM 호출은 느리고 실패할 수 있어 타임아웃, 재시도, 비용 제한, 스트리밍 응답을 설계해야 한다 |

## Day27 (11/24) · RAG 검색 개선 — Query 최적화 · Reranking

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| 실패 진단 | RAG는 단계가 이어진 파이프라인이라 최종 답만 보면 원인을 알 수 없다. 단계별 중간 결과(trace)를 남겨야 처방을 정할 수 있다. 검색 실패에 프롬프트를 고치거나 생성 실패에 리랭커를 붙이는 식의 엉뚱한 처방을 막는다 |
| 쿼리 재작성 | 대화에서 사용자는 맥락을 생략하는데, 검색기는 맥락을 모른다. LLM으로 독립적인 질문으로 바꾸면 재현율이 오른다. 대신 LLM 호출이 하나 늘어 지연·비용이 늘고, 재작성이 원래 의도를 바꾸면(드리프트) 오히려 나빠진다 |
| Multi-query | 질문 표현 하나에 대한 임베딩의 민감도를 여러 표현의 합집합으로 분산시켜 재현율을 높인다. 검색 횟수만큼 비용이 늘고 후보에 잡음도 늘어서, 보통 리랭킹과 짝을 이룬다 |
| 중복 제거 | 같은 조각이 Context를 차지하면 다른 근거가 들어갈 자리가 줄어든다. 여러 검색 결과를 합칠 때는 RRF(순위 역수의 합)처럼 여러 번 나온 문서에 가산점을 주는 방식을 쓰기도 한다 |
| 후보 검색 | 2단계 구조의 핵심 원리는 "1단계는 재현율, 2단계는 정밀도"다. 1단계에서 놓친 문서는 2단계가 되살릴 수 없으므로 1단계 k를 넉넉하게 잡는다. 대신 k를 키울수록 2단계 비용이 비례해 늘어난다 |
| 리랭킹(Reranking) | 비싸지만 정확한 모델을 소수 후보에만 써서 정확도와 비용을 함께 잡는다. 1단계 후보의 품질이 상한이고, 리랭커 추론이 추가 지연(특히 CPU에서)을 만든다 |
| Bi-encoder | 질문과 문서를 **따로** 인코딩하므로 문서 벡터를 미리 계산해 ANN 인덱스에 넣을 수 있다(확장성). 대신 두 텍스트의 단어 간 상호작용을 보지 못해 미묘한 관련성(부정, 조건)을 놓친다 |
| Cross-encoder | 질문과 문서를 **함께** 넣어 모든 토큰이 서로를 보므로(완전한 Attention) 더 정확하다. 미리 계산할 수 없어 후보 수만큼 모델을 돌려야 하므로 전체 검색에는 못 쓰고 리랭킹에만 쓴다. Bi-encoder와 Cross-encoder는 속도와 정확도를 맞바꾸는 짝이다 |
| Before / After 비교 | 같은 질문·같은 Gold·같은 k에서만 비교가 의미 있다. 평균만 보면 일부 질문이 크게 나빠진 것(회귀)을 놓치므로 질문별 변화도 함께 본다. 질문 수가 적으면 작은 차이는 잡음일 수 있다 |

## Day28 (11/25) · RAG 평가

| 용어 | 정의 · 왜 이 방법인가 · 무엇과 맞바꾸나 |
|---|---|
| Gold 데이터셋 | 평가의 기준 자체라 Gold가 틀리면 모든 지표가 틀린다. 사람이 만들면 정확하지만 비싸고 적다. LLM으로 만들면 많고 싸지만 검수가 필요하다. 질문 분포가 실제 사용자 질문과 다르면 높은 점수도 의미가 없다. 그래서 버전(`dataset_version`)을 붙여 같은 버전끼리만 비교한다 |
| 무정답 질문(No-answer) | "근거가 없으면 답하지 않기"는 별도의 능력이라 따로 측정해야 한다. 재현율 0으로 평균에 넣으면 검색 성능이 실제보다 낮게 보이고, 그냥 빼 버리면 "모른다고 말하는 능력"이 평가되지 않는다. `None`(측정 불가)과 `0`(측정했는데 실패)은 다른 정보다 |
| Recall@k | 생성 단계로 넘어갈 근거가 확보됐는지를 본다. RAG에서는 놓친 근거를 뒤에서 되살릴 수 없어 가장 먼저 보는 지표다. k를 키우면 쉽게 오르므로 반드시 k와 함께 보고한다 |
| Precision@k | Context의 잡음 정도를 본다. Gold가 1개뿐인 질문은 k=5에서 최대 0.2라서, 질문마다 Gold 개수가 다르면 평균 해석에 주의한다. 재현율과 맞바꾸는 관계다 |
| 순위 지표(MRR·nDCG) | Recall은 순서를 무시하지만, LLM은 앞쪽 문서에 더 영향받고 Context 자리가 한정돼 있어 순서가 중요하다. MRR은 첫 정답만 보므로 정답이 하나인 질문에, nDCG는 관련도 등급과 여러 정답을 반영하므로 정답이 여럿인 질문에 맞다. nDCG는 등급이 없는 문서를 0으로 처리하면 왜곡되므로 등급 레이블이 완전해야 한다 |
| Claim | 답 전체를 "맞다/틀리다"로 보면 일부만 틀린 답을 구분할 수 없다. 원자적 주장으로 나누면 부분 점수와 틀린 위치를 알 수 있다. 나누는 기준이 사람·모델마다 달라 점수가 흔들릴 수 있다 |
| 근거 일치 | Faithfulness. 답이 **주어진 Context**에 의해 뒷받침되는지 본다. 사실 여부(정답성)와 다르다. Context가 틀렸으면 근거 일치가 높아도 틀린 답이다. 반대로 모델이 사전 지식으로 맞게 답하면 근거 일치는 낮다. 할루시네이션을 측정하는 지표다 |
| 질문 적합성 / 정답성 | 세 지표는 서로 독립적인 축이다. 근거 일치(Context 대비), 적합성(질문 대비), 정답성(Gold 정답 대비)을 따로 봐야 "근거는 충실한데 질문에 안 맞는 답"이나 "맞는데 근거가 없는 답"을 구분할 수 있다 |
| Target / Evaluator | 평가 대상과 채점자를 분리해 정답이 대상 쪽으로 새는 것을 구조로 막는다(평가 누수). LLM을 채점자로 쓰면 규모를 키울 수 있지만, 긴 답 선호·자기 답 선호 같은 편향이 있어 사람 레이블과의 일치도를 먼저 확인해야 한다 |
| 한 번에 하나만 바꾸기 | 변수 통제다. 동시에 여러 개를 바꾸면 효과를 분리할 수 없다. 단, 기능 간 상호작용(둘을 같이 켤 때만 좋아짐)은 하나씩 바꿔서는 보이지 않으므로 아래의 4가지 비교군이 필요하다 |
| 오프라인 / 라이브 | 오프라인 Fixture는 비용 0으로 결정적이라 수식과 코드 검증에 좋다. 하지만 실제 모델·데이터 변화를 반영하지 못하므로 성능 주장의 근거가 될 수 없다. 라이브는 현실적이지만 비용·비결정성이 있어 여러 번 측정하거나 temperature를 고정한다 |
| 실패 단계 진단 | 파이프라인의 앞 단계부터 확인하는 이유는 앞 단계 실패가 뒤 단계 지표를 모두 오염시키기 때문이다. "가장 앞에서 처음 실패한 단계"가 고칠 곳이고, 그 단계의 지표로 수정 효과를 확인한다 |
| invoke | 정의(체인 구성)와 실행(invoke)을 분리하면 같은 체인을 평가·서비스에서 똑같이 재사용할 수 있다. 입력을 화이트리스트로 복사해 넘기면 Gold가 섞여도 구조적으로 걸러진다. "빼야 할 것"을 지우는 블랙리스트보다 안전하다 |
| 4가지 비교군 | 2×2 요인 설계다. 각 기능의 단독 효과와 상호작용 효과(둘 다 켰을 때 − 각각의 효과 합)를 분리할 수 있다. 기능이 n개면 2ⁿ개로 늘어나 비용이 커지므로 중요한 기능만 이렇게 비교한다 |
| 배포 보류(회귀 판정) | 평균이 올라도 특정 질문이 나빠질 수 있다. 질문별 변화량을 보고 "하나라도 크게 나빠지면 보류"처럼 보수적인 규칙을 쓰는 것은, 이미 되던 기능이 깨지는 것(회귀)이 새 기능이 없는 것보다 사용자 신뢰에 더 해롭기 때문이다. 기준을 엄격하게 할수록 배포 속도는 느려진다 |
| Agent 1차 관문 | 검색 Tool을 Agent에 주면 사람이 중간에서 확인하지 않고 그 결과로 다음 행동을 하므로, 단독 RAG보다 기준이 높아야 한다. 정량 지표(Recall·MRR)는 필요조건일 뿐이고, 권한·안전·사람 검토는 지표로 대체할 수 없어 별도 관문으로 둔다 |
